# 0.16.4: clean-up, and what the device test needs

Part 1 of the away batch (`2026-11-24-away-batch.md`; its "Rules for every part" apply).
Written before the code, by the builder, with nobody to ask: every choice the charter left
open is marked **Choice**. Blizzard's source is `~/.cache/wow-ui-source/forever` at
`c01a87b`, build 1.60.1 (71091); paths below are under `Interface/AddOns/`, and
`G/` is `Blizzard_GamepadActionBars/`.

Nothing here is tested on a device. The offline tests prove the logic only.

## 1. Offline check for calls into Blizzard's Lua

`tests/taint/audit.lua`, run by `scripts/test.sh` and (with the source) by
`scripts/audit-api.sh`.

- It reads every `.lua` file in the addon's and the probe's TOC, lists each name that is
  called (`Name(`, `x:Name(`, `x.Name(`, a function handed to `pcall`) or named in a string
  (a hook's target, a function looked up by name), and keeps the names Blizzard defines as
  a Lua function anywhere under `Interface/AddOns` outside the generated documentation.
- Each such name, per file of ours, needs a line in `tests/taint/calls.txt`:
  `name<TAB>file<TAB>verdict<TAB>reason`. An unlisted call fails the check; so does a
  listed call that is gone.
- **Choice: the line number is not stored.** The plan's format had `file:line`; a line
  number moves with every edit and would fail the check for no reason. `--list` prints
  them.
- **Choice: five verdicts, not three.** `clean`, `ours` and `writes` as planned. Added:
  `engine` (the same name, but what we call is a frame's own engine method or a C function,
  or the name is only hooked), because most matches are of that kind (`Show`, `SetPoint`);
  and `writes-known` (it writes, and the call is kept for the reason given). `writes` fails
  the check, so rule 2 is enforced by the test; `writes-known` passes and is printed on
  every run, so a kept write is never out of sight.
- **Choice: `*` as the file** is allowed with `ours` and `engine` only, for names like
  `SetPoint` where the reading is the same everywhere.
- **Choice: it works without the source.** The names Blizzard defines are kept in
  `tests/taint/names.txt` (rewritten whenever the source is there). Without the source a
  called name that is in neither file fails, as the API fast check does.
- The match is by name. What it cannot see (a function reached through a variable, what a
  callee's callee writes) is said in the file's header and in `docs/ARCHITECTURE.md`.
- Existing calls that write are reported to the orchestrator; whether each goes is decided
  per call (see "As built" at the end).

## 2. The Inspect button's picture

Cause, ours. The game draws that button's icon, the atlas `crosshair_inspect_32` or, with
no target, `crosshair_unableinspect_32` (`G/MainActionBarFrame.lua:611-612`), a glyph on a
see-through ground, on a round black disc (`SetupNonBindableSlotBackdrop`, `:415-424`)
inside the slot's ring. `FaceBars.lua` copies only the glyph onto its own square black
backing (`MakePicture`, `pic.back`, black at 0.75). The other three buttons' art fills the
square (a spell icon, `128-redbutton-exit`, `gamepad-ability-icon-jump`), so only this one
reads as a black square; with no target the glyph itself is the dark "cannot inspect" one.

Fix: a picture that shows one of the game's special icons gets a button face under it: a
light rim (the backing) and a grey face (a new texture at the icon's place), the look of
the Jump button's own art. The glyph, its size and colour stay the game's. Spell pictures
and empty squares are unchanged.

**Choice:** every special picture gets the face (the four main-bar buttons and the
targeting bars' buttons), not only Inspect: an addon cannot tell a glyph from art that
fills the square, and art that fills it hides the face anyway. The game's round disc is not
copied: the other three are square.

## 3. Enemy targeting: the B square is empty

Cause, the game's. The assist button's picture is the portrait of the target's target. With
no target of target, or when that is the player, the game hides the picture and switches the
button off (`G/TargetActionBars/Shared.lua:95-105`, called from
`HostileTargetingActionBar.lua:40, 71, 92` on show and on every target change). The hint list
names "B: Assist Target" always. In the screenshot the target is the player's own pet, which
has no target. The empty square is what the game's own bar shows there. **Not changed.**

Found while reading, ours: when the picture is there, it is a unit's portrait, drawn by
`SetPortraitTexture(icon, unit)` (`Shared.lua:98`). `FaceBars.lua` copies an icon by
`GetAtlas` or `GetTexture`; what `GetTexture` returns for a portrait, and whether another
texture can show it, is not in the source. So for a button the game set up to target a unit
(`type` = `"target"` and `unit`, `Shared.lua:112-119`; read with the button's own
`GetAttribute`) our picture is drawn with `SetPortraitTexture` on our own texture
(`Blizzard_APIDocumentationGenerated/UnitDocumentation.lua:572`), and the copy is the
fallback. This covers B (target of target) on both targeting bars and, on the friendly one,
X (pet), A (self) and the four party members.

## 4. Friendly targeting (LB held)

What the source says is drawn:

- LB alone: the game shows the friendly bar in the main bar's anchor and names it the
  active bar (`G/TargetActionBars/StaticOverrideActionBar.lua:183-208`,
  `G/PageUnit.lua:553-562, 587-594`). `FaceBars.lua` then draws state "rest" with the main
  group bound to that bar: the d-pad diamond inner-left, the face diamond inner-right. Not
  in a group the four d-pad buttons are switched off and have no picture
  (`FriendlyTargetingActionBar.lua:164-172`): four empty squares. Face: X the pet's
  portrait (none without a pet), Y the next raid mark, B the target's target (see 3), A the
  player's portrait.
- LB with RT also held: the right trigger's bar is the active one (`G/PageUnit.lua:565-567`;
  a targeting bar only replaces the bar of its own anchor, `StaticOverrideActionBar.lua:175-177`).
  State "rt": the main group's d-pad quiet inner-left (bound to the friendly bar: four
  empty squares), the RT bar's two diamonds on the right, no face half for the friendly bar.

The screenshot `...184427.png` is the second case exactly, and `...184422.png`, five
seconds earlier, shows RT held with the same right side. So RT was almost certainly still
held, and what was drawn is what the game's own state asks for. **Nothing is changed in what
is drawn**, apart from the portraits of 3.

Logging, so the device test settles it: each time the drawn state, the game's active bar or
a group's bar changes, one debug line: the state, the active bar by its name in
`PageUnit.actionBars`, the bar each group follows, and for each half shown its spot, quiet
or not, and how many of its four pictures show an icon. One line per change, never per
frame. The trigger keys themselves are not read (that would be a call into
`Blizzard_Gamepad`'s Lua); the active bar's name says which were held.

## 6. Mark a test section

`PE:MarkSection()`: writes `==== section N ====` to the debug log and says "Section N
marked" in chat. Buttons on the Debug log tab and the Controller tab. **Choices:** with the
Debug log off nothing is counted; chat says to switch it on. **N is kept with the log, not
per session** (a departure from the charter's wording): one sitting has many reloads (a
part switch counts from the next reload, Save reloads), and a count that started again at 1
each time would make "section 1" appear many times in the one file. It starts again at 1
when the log is emptied, which is the first step of the test.

## 7. Save a snapshot

`PE.ControllerLayout:Snapshot()`; buttons on the Debug log tab and the Controller tab (both
rows also show while the layout is off, to record "everything put back"). Out of a fight
only: in a fight it waits for the end (`PE:RunOutOfCombat`) and says so. With the Debug log
off it says to switch it on.

It writes, once:

- a start line with its number and the section;
- the screen's size and UI scale, the active Edit Mode layout's name and whether it is ours;
- every feature's switch and every Controller layout option (all plain values in its saved
  options, so later parts' switches appear without a change here);
- one line per piece: name, shown or hidden, left, bottom, width, height, scale, and its
  see-through when not 1;
- one line per pair of visible pieces that overlap: both names and the overlap;
- an end line with the counts.

Pieces: the game's frames the layout places or moves (map and round map, chat, buffs,
debuffs, quest tracker, XP bars, player, pet, target, target of target, tooltip spot, swing
timers, the four bar anchors and their bars, the two sub-menu buttons, the LB / RB targeting
pictures, the hint box), ours (each spell panel half, the two tap guards, the map's black
disc) and the PE button. Later parts add theirs with
`PE.ControllerLayout:AddSnapshotSource(fn)`. A frame that is not on this client is written
as "not found".

**Choices:**
- Numbers are in UI units from the screen's bottom left (the unit of Edit Mode and of
  `Plan.Rects`), read with each region's own `GetLeft`, `GetBottom`, `GetWidth`, `GetHeight`
  and `GetEffectiveScale`. The charter asks for the overlap in pixels: an overlap line gives
  both, units and screen pixels.
- Overlaps are checked between pieces that are visible and not fully see-through, and not
  between a piece and its own container (the round map in the map, a bar in its anchor) or
  the pairs that lie on each other by design (the tap guards and real bars under the
  panels). Hidden pieces are listed, not checked.
- A value the game hides is written `<secret>` and that piece is left out of the overlap
  check.

## 8. The debug log holds a whole sitting

Found: the cap is 3,000 lines, a ring; when full the oldest line is overwritten, so a long
sitting loses its start. The device's files show about 45 lines per login and 2 to 150 a
minute. A 60-minute test (about 20 reloads, 15 snapshots of about 70 lines, fights, the new
line per trigger change) is 4,000 to 5,000 lines.

- **Cap 6,000** (was 3,000; 10,000 before 0.15.0, lowered for loading time). At about 90
  characters a line that is about half a megabyte in the saved file.
- **When full, the middle goes.** The newest 3,000 lines stay as they are. Of the older
  ones these stay: the first 60 lines of each session, every section mark and every
  snapshot. Each run of dropped lines becomes one line, "---- N lines dropped here: the log
  was full ----" (an older note inside the run adds its count). If what is kept of the
  older part is still more than 1,500 lines, the oldest of it goes too, with the same note.
- The log is now a plain list, oldest first (`next` is always one past the end), so
  `scripts/read-log.sh` reads it unchanged; a ring saved by an older version is put in
  order once at login.
- The Debug log tab says what happens when it is full.

## As built

- **Calls that write.** The check found sixteen. One was removed: `FaceBars.lua` called
  `PageUnit:RegisterActiveActionBarUpdatedCallback` (`G/PageUnit.lua:705`), which writes our
  function into the game's callback table (`Blizzard_SharedXMLBase/CallbackRegistry.lua:112`);
  it now hooks `PageUnit.SetActiveActionBar` (`:527`) with `hooksecurefunc`, the way it
  already follows page changes. **Choice:** the other eight of the addon's (chat lines,
  the chat's font size, opening the chat box, the menu background's callbacks, the bag's
  d-pad route) and the probe's seven are listed `writes-known` and left as they are: none is
  part of the Controller layout, each has been on the device for many versions with no
  refusal while the layout was off, most have no engine-only replacement, and changing them
  with nobody to test is the larger risk. They are for the orchestrator and the owner to
  decide.
- **The snapshot** lists the eight panel halves, not the 32 single pictures (a picture's
  place follows from its half). The file was at Lua's limit of 200 locals, so the snapshot
  lives in a function of its own and hangs on one table.
- **The drawn-state log** is two kinds of line ("drawn:" and "follows:") so each fits the
  log's 200 characters.
