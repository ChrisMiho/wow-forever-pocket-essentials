# Post-0.0.9 batch (version 0.1.0)

Status: **approved by the owner's handoff prompt** (2026-11-17). The owner was
away; every choice the prompt left open is written down here and listed again
under "Choices made without the owner".

Six items from the eighth device test (0.0.9), plus debug-log fixes, built in
order, one commit each, shipped as one GitHub pre-release `v0.1.0`.

## Rules for every item

- Nothing 0.0.9 proved may be undone. With the Gamepad UI on, addon code never
  opens, focuses or closes the chat box. Nothing here touches the chat edit box.
- Controller buttons are only taken or given back out of a fight.
- No libraries. Every handler and callback goes through `PE:Safe` / `PE:Wrap`
  (or the module's `Safe` / `Wrap` / `RegisterEvent` / `After`).
- Nothing ticks while its feature is off. No new per-frame work anywhere.
- New options default to what 0.0.9 does. Saved settings from 0.0.9 carry over.
- Every new game function is looked up in Blizzard's source
  (`~/.cache/wow-ui-source/forever`), then `scripts/audit-api.sh` is run. What
  cannot be confirmed is guarded and logged in `docs/ARCHITECTURE.md`.
- Every new path writes a debug line: `if PE.debugOn then PE:Debug(key, text) end`.
  Never a player's name or chat text.
- Every rule below gets an offline test in `tests/features/`.
  `scripts/check.sh` and `scripts/test.sh` pass after every item.

## 1. A visible "Press A to type" prompt

**Problem.** After a chat button is tapped (Gamepad UI on), the only hint is a
chat line the owner could not read.

**Behaviour.**
- While the A button is lent to the game's OPENCHAT binding, a prompt is on
  screen: a big line "Press A to type" and a smaller line under it saying where
  the chat goes ("Chat is set to Say", "Chat is set to Guild", "Chat is set to
  your whisper").
- It appears when the A button is lent (`TypeKeyArm` succeeds) and goes at the
  same moment the button is given back, for every reason: chat opened, the 12
  seconds are up, a fight started, the feature was switched off. One place in
  the code shows it and one hides it, tied to arm and disarm, so the two can
  never disagree.
- If the A button could not be lent, no prompt (the chat line stays as today).
- The existing chat line stays as well.
- A second tap while the prompt is up replaces the text and restarts the 12
  seconds (as the button lending already does).

**The frame.** The addon's own frame, parent `UIParent`, never a child of a
Blizzard frame. Created on first use. Display only: no mouse, no keys, no
controller navigation mark, strata `HIGH`. Dark rounded-off backdrop is not
needed: a plain dark rectangle behind the text is enough for contrast. Centre
of the screen, 110 pixels (720p) above the middle, sized by `UI:Px` and the
addon's fonts ("title" for the big line, "font" for the small one) so it
follows "Button size". No animation, no `OnUpdate`: the existing 12-second
timer hides it.

**Debug log.** "prompt shown" / "prompt hidden: <reason>" (the kind of chat
only, never who a whisper is for).

**Tests.** Shown after a tap with the Gamepad UI on; text names the target;
hidden when chat opens, after 12 seconds, when a fight starts, on switch-off;
not shown when the button cannot be lent (in a fight) or with the Gamepad UI
off; its parent is `UIParent`; nothing of the chat feature has an `OnUpdate`.

## 2. "One big bag" becomes "Bag sorter"

**Rename.** The feature's name is "Bag sorter" everywhere a player sees it:
the settings row, its description ("Sort your bags with a big button or a
stick click."), status lines, printed messages, README, the CurseForge text,
`docs/TESTING.md`. Lines that describe the game's combined bag itself say "the
combined bag". The feature's key stays `bags` and its saved options stay where
they are, so a saved "on" from 0.0.9 is still on.

**Sort key.** A new option `sortKey`, label "Sort key":

| Value | Label | What it does |
|---|---|---|
| `l3` (default) | Left stick click | 0.0.9's behaviour: `PADLSTICK` sorts while the bag is open |
| `r3` | Right stick click | `PADRSTICK` sorts while the bag is open |
| `none` | Button only | no stick is taken at all |

- `PADRSTICK` is in Blizzard's source (`GamepadConstants.lua`,
  `GAMEPAD_STICK_RIGHT_PRESS`).
- The stick is taken only while the bag is open and handed back when it
  closes, when a fight starts, and when the feature goes off, exactly as now.
- Changing the option while the bag is open swaps the stick at once (out of a
  fight; in a fight it is held with `PE:RunOutOfCombat` like today's
  re-binding). The old stick is always handed back before the new one is taken.
- The on-screen Sort tab is unaffected by this option ("Sort button: Show /
  Hide" stays as it is).
- A saved table from 0.0.9 has no `sortKey`; it reads as `l3`. An unknown
  saved value also reads as `l3`.

**Debug log.** Which stick was taken or handed back, and "no stick taken:
button only".

**Tests.** Label is "Bag sorter"; no player-visible text of the feature says
"One big bag"; each of the three values binds the right key (or none) on bag
open and clears it on close; changing the value with the bag open swaps it;
a 0.0.9 saved table (no `sortKey`) binds L3; the tab is there in all three.

## 3. Chat font size

**Behaviour.** In the settings, inside the "Big chat buttons" block, a row
"Chat text size" with the current size and two big buttons, "Smaller" and
"Bigger". Each tap moves one step through 12, 14, 16, 18, 20, 24, 27 (the
game's own list, `CHAT_FONT_HEIGHTS`) and then on to 30 and 34, so it can go
larger than the game's own menu. At either end the button does nothing more.
A current size that is not on the list moves to the next listed size in the
tapped direction.

**How.** The game's own function, `FCF_SetChatWindowFontSize(nil, chatFrame,
size)` (`Blizzard_ChatFrameBase/Mainline/FloatingChatFrame.lua:1090`). By the
source it reads the frame's font, sets it at the new size (also on the GM and
Communities chat when the frame is the main one) and calls
`SetChatWindowSize`, which is how the game remembers the size itself. It
contains no protected call and never touches an edit box. It is applied to
every chat window (`ChatFrame1` to `NUM_CHAT_WINDOWS`) that exists, so all
tabs match.

- The addon stores nothing: the game saves the size. With no tap, nothing is
  changed (today's behaviour).
- The current size is read from the main chat window's font (`GetFont`).
- Applied only out of a fight (`PE:RunOutOfCombat`), since safety with the
  Gamepad UI on is proved only by reading, not on the device.
- The chat edit box is never touched.
- If the function or the main chat window is missing, the row says "Not
  available on this version of the game" and has no buttons.

**Settings support.** Option rows gain one new kind so a feature can show a
row of action buttons with a value text, without feature-specific code in
`Settings.lua`: `{ label = "...", value = function(mod) -> text, buttons = {
{ label, action = function(mod) }, ... } }`.

**Unverified, to log in `docs/ARCHITECTURE.md`.** Whether sizes above 27 are
kept across a reload; whether calling the function from addon code with the
Gamepad UI on has any after-effect (the source shows none). Worst case: the
size falls back after a reload, or a block report names it in the next log.

**Debug log.** "chat text size 18 -> 20 (N windows)", "held for after the
fight", "not available".

**Tests.** Bigger and Smaller step through the list and stop at the ends; an
off-list size snaps in the right direction; every existing chat window gets
the size; in a fight nothing is applied until it ends; the edit box is not
touched; missing function shows the "not available" text.

## 4. The quest arrow follows the player

### What was found (systematic debugging, before any design)

Evidence: the 0.0.9 device log (quest 745, "Sharing the Land", focused for 25
minutes in Mulgore) and an offline replay of the same quest from QuestieDB.

1. **Finished objectives do drop out.** In the device log the icon count
   falls (292, 286, 279, 277) as parts of quest 745 are finished, and offline
   a finished objective's spots are gone after the next quest-log event. The
   existing test "after the player moves next to a different spot ... it
   points at that one" passes, and an offline walk across quest 745's three
   camps re-picks the nearest spot every second. So the two faults could
   **not** be reproduced as a plain bug in the picking code.
2. **The log cannot show what the arrow did.** Its line reads "pointing at
   quest 745 ... (nearest spot)" and is only written when that text changes,
   so the spot never appears. This is why the device log cannot confirm or
   deny the fault.
3. **The real cause of "stays on the first one": the arrow has no memory.**
   A spot is a place where a creature or object appears. Quest 745 has 26
   spots in three camps. Standing in a camp, the nearest spot is always one
   under the player's feet, so the arrow reads "Here" or points a few yards
   away for as long as the player is in that camp, even when everything there
   is dead, and it points back at the camp until the player is more than half
   way to the next one. It never says "you have done this place, go on".
4. **No steadiness.** The pick is "nearest, full stop". Between two spots at
   a similar distance it can swap every second.
5. **A rebuild replaces every spot.** Each kill rebuilds the quest's spots as
   new tables, so the arrow treats its target as new each time ("Here" is
   reset and re-entered).

### Design

All inside the existing once-a-second pick (`SELECT_INTERVAL`); the 10-a-second
draw is unchanged and nothing new runs per frame.

- **Spot identity.** A spot is known by its map position and objective, not
  by its table, so the target survives a rebuild. If the current target's
  position is still among the quest's spots after a rebuild it stays the
  target, and "Here" is not reset.
- **Finished objectives drop at once.** On the quest-data "quests" callback
  the pick is redone on the next update (as now). If the current target is no
  longer among the spots, the nearest remaining spot is taken immediately,
  with no steadiness margin.
- **Steady re-pick.** Each second, if the player has moved: the nearest
  remaining spot replaces the current one only when it is at least 20 %
  nearer **and** at least 15 yards nearer. While the arrow reads "Here" the
  target never changes.
- **Moving on from a reached spot.** When the arrow has read "Here" at a spot
  and the player then leaves it (beyond the existing 14 yards), that spot is
  set aside for 180 seconds: it is skipped by the pick, so the arrow leads to
  the nearest spot not yet reached. Spots are set aside by position, so
  rebuilds do not bring them back early. If every spot on this map is set
  aside, the list is cleared and the nearest is picked again (a quest with one
  spot, such as a turn-in, behaves as today). The list is cleared when the
  focused quest changes, the map changes, or the feature goes off. It is a
  small table checked only in the once-a-second pick; expired entries are
  dropped there.
- **Icons.** The spot the arrow points at keeps its icon as today
  (`QD:SetArrowPin`). Set-aside spots keep their icons; only the arrow skips
  them.
- **Objective number.** Each spot carries `obj`: the number of its objective
  in the game's quest log (nil for a turn-in spot or when no log objective
  matched). `QuestData.lua` already finds this match (`ObjectiveState`); it
  now also hands the number on. Used for the log line and spot identity.

### Arrow debug log (also the "small fixes" for the arrow)

- The pointing line names the spot: "pointing at quest 745 objective 2 spot
  46.5,73.5 on map 1412 (nearest of 16, 3 set aside)". Because the text
  includes the spot, a line is written each time the spot changes (at most
  once a second, by the pick's cadence).
- Why it changed, one line each: "spot changed: objective finished or spot
  gone", "spot changed: another is nearer (120 yd against 310 yd)", "spot set
  aside for 180 s after being reached", "all spots reached: starting again".
- "driver started" / "driver stopped" are written only on a real change: not
  when a quest-log event makes the driver start and stop again in the same
  text-only state (the pair that floods the log with no quest focused).

### Tests

Finished objective: its spots are gone and the arrow is on a remaining
objective's spot after the next update, no extra second. Same target kept
across a rebuild that keeps the spot. Steadiness: two spots at a similar
distance do not swap as the player steps back and forth across the midpoint;
a clearly nearer spot does take over after a second. Reached spot: after
"Here" then leaving, the arrow goes to another spot, not back; after 180
seconds the spot is eligible again; all set aside clears the list; a one-spot
quest keeps pointing at its spot. Focus change clears the list. Log lines
name objective and coordinates and are written on each change, and no
started/stopped pair is written for a quest-log event with no quest focused.
Nothing ticks more often than before (existing tick tests stay green).

## 5. Collapsible feature sections

**Behaviour.**
- Each feature's row is its header: the name and the ON / OFF switch, as now.
- A feature that is on and has options gets a big button in its header row,
  left of the switch: "Hide options" when open, "Show options" when folded.
- Folded: the options block and the description line are hidden. The name,
  the switch (showing ON), and any warning or status line (a problem, "reload
  needed") stay. Folding never changes whether the feature is on.
- Features that are off have no options showing and no fold button, as now.
- Remembered between sessions in `PocketEssentialsDB.ui.folded[<feature key>]
  = true`. Default: unfolded (today's look). A missing or wrong-typed table is
  replaced by an empty one.
- Controller: the button is an ordinary settings button, so it is in the
  window's d-pad order and A presses it. After folding or unfolding, the
  controller's highlight stays on that same button.

**Debug log.** "settings: <key> folded" / "unfolded".

**Tests.** Fold hides the options and keeps the switch showing ON; the feature
is still enabled; unfold brings them back; the state survives a reload (saved
table); a feature that is off has no fold button; a feature with no options
has none; the fold button is in the controller list and the highlight stays
on it; a bad saved `folded` value does no harm.

## 7. Debug-log fixes in the core

- **Timestamps.** The milliseconds come from a different clock than the
  seconds, so lines within a second can look out of order. Fix: both come
  from one clock. On the first line of a session the wall clock (`time()`) is
  paired with the game's timer (`GetTime()`); every stamp is that pair's start
  plus the timer's progress, split into `HH:MM:SS` and `.mmm`. Stamps never go
  backwards within a session.
- **Fight legend.** The "(kinds: 0 combat, ...)" legend is written with the
  first restriction line of a session only; later lines are just "addon
  restriction 0 is now 1".
- `scripts/read-log.sh` and its tests keep working (the line format is
  unchanged).

**Tests.** Stamps in one session are non-decreasing across second boundaries
with a timer whose fraction is offset from the wall clock; the legend appears
once per session and again in a new session.
