## 1. Chat text size

#### What the player sees
In the addon's settings, in the "Big chat buttons" block, the row "Chat text size" changes from two
buttons to a row of size buttons:

```
Chat text size: 18
[12] [14] [16] [18] [20] [24] [27] [Smaller] [Bigger]
```

- The seven number buttons are exactly the sizes in the game's own chat tab menu (Font Size). The
  one matching the chat's size right now is highlighted, the same way "Button size" highlights
  Small / Medium / Large.
- Tap a number: every chat window changes to that size at once, and the game remembers it exactly as
  if the tab menu had been used. Nothing to confirm, no reload.
- "Smaller" and "Bigger" stay and work as today (one step at a time, and on past 27 to 30 and 34,
  which the game's menu does not offer). They are the only way to reach 30 and 34.
- The row is shown **whether "Big chat buttons" is ON or OFF**. It only does something when tapped,
  so it does not need the feature. (Today it is hidden while the feature is off.)
- "Hide options" / "Show options" folds it away like any other option.

#### Exact labels
- Row text: `Chat text size: <number>`; in a fight after a tap: `Chat text size: <number> (after the fight)`.
- Buttons: the plain numbers `12` `14` `16` `18` `20` `24` `27`, then `Smaller`, `Bigger`.
- When the game lacks the function or the main chat window: `Chat text size: Not available on this
  version of the game`, no buttons (unchanged).

#### Rules
1. **The sizes come from the game.** The number buttons are read from the game's own list each time
   the settings window is drawn. If that list is missing or damaged, the addon uses its own copy:
   12, 14, 16, 18, 20, 24, 27. The game's list is never written to.
2. **All chat windows, same size.** The game's tab menu changes only the one tab that was clicked;
   to do the whole chat the player has to repeat it per tab. Our button does all ten chat windows the
   game keeps (General, Combat Log and any others, shown or not) in one tap, which is the point of
   the request ("easier"). This is what Smaller / Bigger already do.
3. **The current size is read from the game, never from the addon.** The highlighted button and the
   number in the row text come from the main chat window's font at the moment the window is drawn
   (the same reading the game's own menu uses to tick its entry). The addon saves nothing, so the
   two can never disagree. If the size is one the buttons do not have (30, 34, or something another
   addon set), no number is highlighted and the row text still shows the true size.
4. **Tapping the highlighted size still applies it.** Useful when another tab was set to a different
   size from the tab menu: one tap makes them all match again.
5. **One path.** Number buttons and Smaller / Bigger end in the same function, which calls the
   game's own `FCF_SetChatWindowFontSize` once per window. There is no second way in.
6. **Fights.** A tap in a fight is held and applied when the fight ends; the row shows the waiting
   size with "(after the fight)" and highlights it. The last tap wins. Smaller / Bigger keep
   stepping from the waiting size.
7. **Nothing happens on login.** No size is applied unless a button is pressed. Nothing ticks, no
   event is listened for, with the feature on or off.
8. The chat typing box is never touched.

#### Debug log lines (key "chat")
- `text size 18 -> 20 (10 windows)` - a change was applied (unchanged wording; also written for a
  tap on the highlighted size, e.g. `text size 18 -> 18 (10 windows)`).
- `text size change held for after the fight` (unchanged).
- `text size 34: already the biggest` / `text size 12: already the smallest` (unchanged, Smaller / Bigger only).
- `text size: not available` (unchanged).
- New: `text size: the game's size list is missing, using our own` - written on a tap when the
  fallback list was used.

#### What only the device can prove
- That the row of nine buttons fits and is comfortable to reach with touch and the d-pad at the
  Small, Medium and Large button sizes (it will wrap onto two or three lines).
- That every listed size survives a reload and a full log-out.
- That the game's tab menu ticks the same size afterwards (the two agree).
- That it works with "Big chat buttons" OFF.
- That a tap in a fight applies when the fight ends, with no "action blocked" report.
- Still open from 0.1.0: whether 30 and 34 survive a reload.

#### Question for the owner (one)
Keep "Smaller" and "Bigger" beside the numbers (recommended: they are the only way to 30 and 34 and
removing them was not asked for), or drop them for a tidier row of seven?

### Findings in Blizzard's source

#### The game's size list
- `Blizzard_ChatFrameBase/Mainline/FloatingChatFrame.lua:33-41`: global table
  `CHAT_FONT_HEIGHTS = { 12, 14, 16, 18, 20, 24, 27 }`. Seven sizes. This is the Mainline file, which
  this client loads (`Blizzard_ChatFrameBase.toc:47`, `[Family]\FloatingChatFrame.lua`).
- `FloatingChatFrame.lua:31`: `CHAT_FRAME_DEFAULT_FONT_SIZE = 18` (the size of a fresh window).

#### How the tab's Font Size menu works
- `FloatingChatFrame.lua:536` `FCF_Tab_SetupMenu(self)` builds the menu that opens from a chat tab.
- `FloatingChatFrame.lua:643-662`: the "Font Size" submenu.
  - Which entry is ticked: `currentChatFrame:GetFont()`, height rounded with `floor(h + 0.5)`
    (lines 647-651). So the game itself reads the current size from the window's font.
  - Picking an entry: `FCF_SetChatWindowFontSize(nil, tabChatFrame, height)` (line 654), where
    `tabChatFrame` is the window whose tab was clicked (line 553). **The tab menu changes one window
    only.**
  - One radio entry per item of `CHAT_FONT_HEIGHTS` (lines 657-661), labelled with
    `format(FONT_SIZE_TEMPLATE, height)`. `FONT_SIZE_TEMPLATE` is a translated text that is not in the
    source repo, so the addon should not depend on it.
- `FloatingChatFrame.lua:1090-1109` `FCF_SetChatWindowFontSize(self, chatFrame, fontSize)`:
  1. `chatFrame:GetFont()` then `chatFrame:SetFont(fontFile, fontSize, fontFlags)`;
  2. if the window is `DEFAULT_CHAT_FRAME`, the same font goes on `GMChatFrame` and
     `CommunitiesFrame.Chat.MessageFrame` when those exist;
  3. `SetChatWindowSize(chatFrame:GetID(), fontSize)` (line 1108): the game's own (C side) saver.
  With `chatFrame` nil it falls back to `FCF_GetCurrentChatFrame()`, with `fontSize` nil to
  `self.value`; the addon always passes both, so neither fallback is reached.

#### How the game remembers and restores it
- Saved by `SetChatWindowSize` (C function, no Lua source; the only caller is line 1108).
- Read back by `GetChatWindowInfo(id)` inside `FCF_GetChatWindowInfo` (`FloatingChatFrame.lua:448-469`;
  a saved 0 means the default 18, line 462-464).
- Applied at login/reload on the `UPDATE_CHAT_WINDOWS` event:
  `Blizzard_ChatFrameBase/Mainline/ChatFrameOverrides.lua:118-123` (each chat window sets its font
  from the saved size) and `Blizzard_GMChatUI/Blizzard_GMChatUI.lua:127-132`.
- Windows 1 to `Constants.ChatFrameConstants.MaxChatWindows` (10) are saved this way;
  `NUM_CHAT_WINDOWS` is the same number (`Blizzard_DeprecatedChatInfo/Deprecated_ChatFrame.lua:18`).
  Temporary windows (id above 10, e.g. a whisper popped out into its own window) are not saved by
  the game (`FloatingChatFrame.lua:449-459`) and are copied from another window when made (line 481).

#### Is it safe to call from addon code
- By reading: no protected call, no secure-frame work, no edit box, no `InCombatLockdown` or
  `issecure` check anywhere in the function (grep of the file shows only "secret name" handling for
  tab titles, lines 72-76, 1019, 2273, 2386, which this path does not touch).
- By the device: the 0.1.0 log shows it working on all ten windows with the Gamepad UI on, no block
  report (PRD.md:393-397).
- Still unknown (already logged in `docs/ARCHITECTURE.md:146-147`): whether `SetChatWindowSize` is
  restricted in a fight. The addon therefore only applies out of a fight (`PE:RunOutOfCombat`,
  `Core.lua:405`). Keep that.

#### API names used, and their audit status
| Name | Where | In `tests/api/verified.txt` today |
|---|---|---|
| `FCF_SetChatWindowFontSize` | FloatingChatFrame.lua:1090 | yes (line 62) |
| `NUM_CHAT_WINDOWS` | Deprecated_ChatFrame.lua:18 | yes (line 48) |
| `DEFAULT_CHAT_FRAME` | ChatFrameUtil.lua | yes (line 35) |
| `GetFont` (method) | widget API | yes (line 108) |
| `CHAT_FONT_HEIGHTS` | FloatingChatFrame.lua:33 | **no** - new read; run `scripts/audit-api.sh` |

No other new game name is needed. `FCF_GetChatWindowInfo`, `GetChatWindowInfo`, `SetChatWindowSize`
and `FONT_SIZE_TEMPLATE` are deliberately not called by the addon.

### Risks and unknowns

- **Layout.** Nine buttons in one row will wrap to two or three lines (each button is at least 2.2
  button-heights wide, `Settings.lua:148`). Readable, but the block gets taller; only the device can
  say whether it feels right. If not, the fallback is dropping Smaller / Bigger (the owner question).
- **Reversing an earlier decision.** 0.1.0 deliberately hid the row while the feature is off (old
  spec section 3, test at chat_test.lua:951). Showing it regardless needs the new `always` row flag
  in `Settings.lua`, which touches the code that draws every feature block and its fold button; the
  d-pad order and fold memory for all features must be re-checked on the device. The cheaper
  alternative is to keep the old rule (row only while the feature is on) and change nothing in
  `BuildModuleRow`; the owner's "standalone" wording argues against it.
- **`SetChatWindowSize` is a black box** (C side). Listed sizes are what the game's own menu sends,
  so they are safe; 30 and 34 across a reload are still unproved. Fight behaviour is unproved, hence
  the hold until the fight ends.
- **All windows, including Combat Log.** The Combat Log tab changes size too (as it has since
  0.1.0). A player who wanted different sizes per tab loses that on a tap; the game's tab menu still
  allows it afterwards, and our row then shows the main window's size only.
- **Temporary chat windows** (a whisper popped out into its own window, id above 10) are not
  changed; the game does not save their size either.
- **The game's list could change** in a later build (more or fewer sizes); the row follows it, and a
  very long list would make the row tall. An empty or damaged list falls back to the seven.
- **Another addon changing chat fonts** could leave the main window at an odd size; the row then
  shows that number with nothing highlighted, which is correct but may look odd.
- **Off-device tests prove the logic only.** The stand-in for `FCF_SetChatWindowFontSize` is a copy
  of the source, not the game.

## 2. Menu background

#### What the player sees

A new switch on the settings page:

- **Name:** Menu background
- **Text under it:** Puts a dark panel behind the game's pop-up menus, such as the menu on a quest in the quest log, so the text is easy to read.
- **Starts off.** No reload needed to turn it on or off.

With the switch on: whenever one of the game's pop-up menus opens (the quest log's Track / Focus / Share / Abandon menu is the one that matters), a plain, nearly black panel with a thin grey edge sits right behind it, the same size as the menu plus a small margin. When the menu closes, the panel goes away with it. A side menu that opens from a menu entry gets its own panel.

With the switch off: nothing is added and nothing runs.

#### Rules

1. The panel is ours: a flat colour (0.05, 0.05, 0.05, 95% solid) with a 1-unit edge (0.52, 0.52, 0.57), the same look as the label behind our map icons. No game art is used.
2. The panel follows the menu: it is pinned to the menu's four corners (6 units wider on each side, 3 units taller top and bottom, which is inside the area Blizzard's own background would have covered), so it is always the menu's size even if the menu changes size while open.
3. The panel is drawn just under the menu and above everything the menu covers (same layer group as the menu, one level lower).
4. The panel never takes taps or clicks.
5. The menu's entries are not touched. Track, Focus, Share, Share in Chat and Abandon keep working exactly as now; the addon only listens for "a menu was shown / hidden".
6. It applies to all of the game's pop-up menus of the new kind, not only the quest log's, because they are all built by the same code and very likely all lack the background. If one of them does have its own background, ours sits hidden behind it and changes nothing.
7. If the game does not offer the "menu shown" announcement on this client, the feature does nothing, quietly, and writes one line in the debug log. It does not show a problem on the settings page.
8. The panel appears in or out of a fight alike (it is only a picture; it needs nothing a fight restricts).
9. Turning the switch off hides every panel at once and stops listening.
10. At most 6 panels exist at a time (a menu and its side menus never need more). They are made the first time they are needed and reused.

#### Debug-log lines (key `menuBg`)

Written only while the debug log is on.

| Line | Meaning |
|---|---|
| `menuBg: feature on` / `feature off` | From Core, as for every feature. |
| `menuBg: game background art "common-dropdown-bg": missing` (or `present`, or `cannot tell`) | Once per switch-on. Settles the hypothesis in 1.4. |
| `menuBg: listening: shown yes, hidden yes, closed yes, quest hook yes, manager yes` | Once per switch-on; each `yes/no` says whether that piece exists on the client. |
| `menuBg: cannot listen for menus on this client; doing nothing` | Once, when neither way of listening is available. |
| `menuBg: panel shown (announcement), menu 212 x 148, layer FULLSCREEN_DIALOG level 503, panels in use 1` | A menu opened and the main path ran. |
| `menuBg: panel shown (quest hook), menu ...` | The main path did not run for the quest menu; the fallback did. |
| `menuBg: quest menu opened, panel already there` | First time only per switch-on: both paths work (the fallback had nothing to do). |
| `menuBg: quest hook ran but no open menu was found` | Fallback could not find the menu. |
| `menuBg: panel hidden (hidden)` / `(closed)` / `(menu gone)` / `(switched off)` | Which signal removed the panel. `menu gone` means no closing announcement came and the tidy-up caught it. |
| `menuBg: menu skipped: forbidden` / `no room (6 panels in use)` | A menu we chose not to touch. |

To keep the log short: after the first 20 "panel shown" lines in a session, only a count is kept and printed in the next `feature off` line (`menuBg: 57 menus got a panel since switch-on`).

#### What only the device can prove

- That the panel is visible at all, sits behind the text and in front of the quest list, and has the right size.
- That Track, Focus, Share in Chat and Abandon still work with the controller and no "Interface action failed because of an AddOn" line appears, in and out of a fight.
- Whether the game's background art is really missing (the log line).
- Whether other menus (right click on a player, a chat tab) had the same fault and now look right, and whether any menu that already had a background looks wrong with ours behind it.
- That the panel always goes away when the menu closes (pick an entry, press B, close the map while the menu is open).

### Findings in Blizzard's source

#### 1.1 What opens the menu

It is the new Menu system (`Blizzard_Menu`), not the old `UIDropDownMenu`.

- `Blizzard_UIPanels_Game/Mainline/QuestMapFrame.lua:2367` `QuestMapLogTitleButton_CreateContextMenu(self, parent)` builds it with `MenuUtil.CreateContextMenu(menuParent, generator)` (line 2373), tag `"MENU_QUEST_MAP_LOG_TITLE"` (line 2374). The entries match the owner's list exactly: Track/Untrack (2379-2384), Focus / stop focus via `C_SuperTrack` (2386-2394), Share Quest (2396-2401), Share in Chat, only when the Gamepad UI is on (2403-2410), Abandon Quest (2412-2416).
- Two callers, both by global name:
  - `QuestMapFrame.lua:2501` (a right click on a quest title, `QuestMapLogTitleButton_OnClick`).
  - `Blizzard_WorldMap/Blizzard_WorldMap.lua:906-923` `WorldMapMixin:OpenQuestOptions()`, bound to the controller's top face button (lines 1109, 1133, 1137). This is the path the handheld uses.
- With the Gamepad UI on, the menu is then re-anchored under the quest row or beside the details pane (`QuestMapFrame.lua:2419-2425`).
- "Camelot" is in the "mainline" family: TOC lines such as `Blizzard_UIPanels_Game/Blizzard_UIPanels_Game.toc:44` read `[AllowLoadGameType mainline] [ExcludeLoadGameType camelot]`, which only makes sense if camelot is otherwise included in mainline. So the `Mainline/` files apply unless a line excludes camelot.

#### 1.2 How the menu frame is made and shown

- `Blizzard_Menu/MenuUtil.lua:151-160`: `CreateContextMenu` picks a style mixin (`ownerRegion.menuMixin or MenuVariants.GetDefaultContextMenuMixin()`, line 148), builds the description, then opens it through the menu manager.
- `Blizzard_Menu/Menu.lua:2205-2283` `MenuManagerMixin:AcquireMenu`: takes a pooled frame of template `MenuTemplateBase` (line 2198), mixes the style mixin into it and calls its `Generate()` (lines 2200-2203), sets strata `FULLSCREEN_DIALOG` (2248-2257). The frame has no parent (`frame:SetParent(nil)`, line 2187); only the scale of the top-level parent is copied.
- `Menu.lua:2461-2569` `GenerateMenuInternal`: positions it, sets `OnShow`/`OnHide` scripts to `MenuProxyMixin.OnShow/OnHide` (2528-2529), sets the frame level to owner level + 500 + menu level (2518-2531), then `proxy:Show()` (2532).
- On this client the template is `Blizzard_Menu/Camelot/Menu.xml` (TOC: `Menu.xml [ExcludeLoadGameType camelot]`, `Camelot\Menu.xml [AllowLoadGameType camelot]`). It differs from the normal one only by controller extras: `FocusFramesInterfaceMixin`, a `FrameGlow` and three jump-hint child frames, and a `layoutType` key. It contains no background art of its own.
- The "A Select / B Close" bar is a separate footer made in `Menu.lua:1829-1834`.

#### 1.3 How the background is meant to be drawn

Only by the style mixin's `Generate()`; nothing else draws one.

- `Blizzard_Menu/Blizzard_Menu.toc`: `[Family]\MenuVariants.lua [AllowLoadGameType mainline]` gives camelot `Blizzard_Menu/Mainline/MenuVariants.lua`, whose lines 1-7 return `MenuStyle1Mixin` for both dropdown menus and context menus.
- `Blizzard_Menu/Mainline/MenuTemplates.lua:51-60`:
  `MenuStyle1Mixin:Generate()` attaches one texture, `background:SetAtlas("common-dropdown-bg")`, stretched 10 px past the left and right and 3 px past the top and bottom of the menu, alpha 0.925. That single atlas is the whole background. It is not a nine-slice and there is no border piece.
- For comparison, the other style, `MenuStyle2Mixin` (`Blizzard_Menu/MenuTemplates.lua:1186-1193`), uses atlas `common-dropdown-c-bg`. Two flat-colour test styles also exist in the same file (`BlackColorStyleMenuMixin`, lines 1177-1184), which shows Blizzard's own menu code is happy with a plain colour behind a menu.

#### 1.4 Hypothesis

**Most likely (not proven): the atlas `common-dropdown-bg` does not exist in this client's art files.** The Lua comes from the modern code base, the art from an older game. `SetAtlas` with an unknown name raises no error and draws nothing (the addon already relies on that fact, `addons/PocketEssentials/Bags.lua:458-464`). The text and the highlight still show because they use plain texture files and fonts (`Blizzard_Menu/MenuVariants.lua:16-52`), which fits "works but no background".

If this is right, **every** menu from the new Menu system that uses the default style has the same fault (right click on a player, chat tab menus, dropdown lists), not only the quest log's. The owner has only reported the quest one. That is consistent (on a controller the others are rarely opened) but it is not confirmed.

Less likely alternatives, which the proposed fix covers equally because it does not depend on the cause:
- The atlas exists but its texture file is missing or blank.
- A camelot-only file not in the public source replaces `MenuVariants.GetDefaultContextMenuMixin` with a style that draws nothing. (If the Mainline variant did not load at all, the base file's version raises an error, `Blizzard_Menu/MenuVariants.lua:72-82`, and the menu would not open; it does open.)

The source cannot settle this (there is no art in the repository). The build below writes one debug-log line that settles it on the device: the result of `C_Texture.GetAtlasInfo("common-dropdown-bg")`.

#### 1.5 Hooks Blizzard offers, and how safe each is

| Hook | Where | Carries | Safety |
|---|---|---|---|
| `EventRegistry` event `"MenuProxy.OnShow"` | `Menu.lua:1845-1849`, fired from the menu frame's `OnShow` | the menu frame | Callbacks run through `securecallfunction` (`Blizzard_SharedXMLBase/CallbackRegistry.lua:198-214`), so our code cannot taint the menu's own code path. Fires for every menu and submenu. |
| `EventRegistry` event `"MenuProxy.OnHide"` | `Menu.lua:1851-1853` | the menu frame | same |
| `EventRegistry` event `"MenuProxy.OnClose"` | `Menu.lua:1755` | the menu frame, close reason | same |
| `hooksecurefunc("QuestMapLogTitleButton_CreateContextMenu", fn)` | global at `QuestMapFrame.lua:2367`; both callers use the global name | the quest button | Taint-safe by design; runs after the menu is open and anchored. Quest menu only. |
| `Menu.GetManager():GetOpenMenu()` | `Menu.lua:2712`, `2667-2671` | the open root menu frame (the frame is its own proxy, `Menu.lua:2219-2226`) | read only |
| `Menu.ModifyMenu(tag, cb)` then `rootDescription:AddMenuAcquiredCallback(cb)` | `Menu.lua:2767-2788`, `487-493` | owner, description; then the menu frame | Documented for addons, but it puts our function inside the menu's description. More contact than needed; **not used**. |

Things that must be avoided, with the reason:
- **No child frame under the menu, and no frame created with a Blizzard parent.** The controller navigation hooks `CreateFrame` and acts on any frame created with a parent (`Blizzard_GamepadSmartNavigation/SmartNavigation.lua:255-265`; already logged in `docs/ARCHITECTURE.md:145`). The menu frames themselves have no parent, so ours need none either.
- **No `HookScript`/`SetScript` on the menu frame.** Blizzard re-sets `OnShow`/`OnHide` with `SetScript` on every open (`Menu.lua:2528-2529`), and the frames are pooled and reset (`Menu.lua:2182-2194`).
- **No writes to the menu frame's table, no `CreateTexture` on it.** The pooled frame is reset with `SetToDefaults()` and its regions are managed by Blizzard's "compositor"; the controller navigation checks `issecure()` (`SmartNavigation.lua:74-88`) and the device has already shown "Interface action failed because of an AddOn" in this area.
- **No replacing of `MenuVariants.GetDefaultContextMenuMixin`** or of any Blizzard function.

### Risks and unknowns

1. **Taint (the biggest).** The controller path that opens and drives this menu checks that it runs "clean" and prints "Interface action failed because of an AddOn" otherwise; the device has shown that message before in controller-navigation code. The design keeps clear of it: callbacks arrive through `securecallfunction`, the panel is our own parentless frame, nothing is written to or created on the menu, no Blizzard function is replaced. By the source this is safe, but only steps 5-13 on the device prove it. If a block appears, the saved log's blocked-action report will name the line; the switch is off by default, so no player is affected meanwhile.
2. **Layering.** The panel is a separate frame one level under the menu in the same strata. The menu template has `flattenRenderLayers="true"` and controller glow children at fixed levels 505/515 (`Blizzard_Menu/Camelot/Menu.xml`); by the rules of frame levels the panel is still under the menu's text and over the quest log, but this client's renderer is the one thing the source cannot show. Symptom if wrong: panel shown in the log but invisible, or drawn over the text.
3. **Windows.** Menus call `proxy:SetWindow(window)` (`Menu.lua:2259-2277`; `GetWindow`/`SetWindow` are in `SimpleFrameAPIDocumentation.lua:635`, `:1529`). Our frame stays in the default window. On a single-screen handheld these should be the same. `SetWindow` is deliberately not called (its arguments are restricted for tainted code). Symptom if wrong: logged as shown, not visible.
4. **A parentless frame of ours** has not been used in this addon before. Blizzard's own menus are parentless and visible, including over the full-screen map, which is why it was chosen (a frame under `UIParent` could be hidden with it). Unverified on the device.
5. **The hypothesis itself** (missing `common-dropdown-bg`) is unproven. The fix does not depend on it; the log line settles it.
6. **Scope.** The panel goes behind every menu of the new system. If some menus do have working backgrounds (a different style, `common-dropdown-c-bg`, drawn 17 px wider than the menu), ours is hidden behind them. If one has a semi-transparent or oddly shaped background, ours could show through as a darker box. Device step 12. A narrower rule (quest log only, by checking `Menu.GetOpenMenuTags()`, `Menu.lua:2790`) is possible later; it was left out because it adds a call into the menu system for no known benefit.
7. **A lingering panel.** If a menu closes with no announcement, the panel stays until the next menu opens (main path) or up to a quarter of a second (fallback path). By the source both announcements always fire (`Menu.lua:1755`, `:1758`, `:1851`).
8. **Later game patch.** If Blizzard adds the art, both backgrounds are drawn, ours hidden behind theirs; the owner can switch ours off. If Blizzard renames the events, the feature goes quiet and the log says so.
9. **Not checkable by the tools; add to the unverified table in `docs/ARCHITECTURE.md` (format as line 141):**

## 3. D-pad to the Sort tab

### In short

- **Moving onto the tab with the d-pad can be done the way Blizzard does it for its own bag picture button** (a "jump override"), and by Blizzard's source it does not taint item use.
- **Pressing it with A does not work by itself.** While the bag has controller focus, A belongs to the bag's own "Select" action, which only fires for buttons carrying the bag's own tag. Ours cannot carry that tag cleanly. So the addon must take A for itself while the tab is focused, the same way it already takes the stick click.
- Whether our hold on A beats Blizzard's hold on A cannot be read from the source. Only the device can say. If it does not, the feature is not worth shipping (you could reach the tab but not press it).
- The other "supported" route (registering our tab as its own window with Blizzard's focus manager) is **proven harmful on this device** and is rejected.

---

#### What the player sees

- New choice in the "Bag sorter" row: **"D-pad to Sort": Off (default) / On.** Off until it has passed a device test.
- With it on, the Gamepad UI on, the bag open and the Sort tab showing: pressing **Left** on the d-pad from any item in the bag's first (leftmost) column moves the game's own controller cursor onto the Sort tab.
- On the tab, **A** sorts the bags (same sound, same sort, same half-second guard as a tap). **Right** goes back into the bag (to the first-column slot level with the middle of the tab). **B** still closes the bag. Up, Down and Left do whatever the game does (it will hop to some bag slot; it cannot get stuck).
- Touch and the stick click keep working exactly as now.

#### Rules

1. Nothing changes for using, picking up, selling or equipping items. Our code never touches those buttons' own actions.
2. From the first column, Left used to wrap round to the last column. With this on it goes to the Sort tab first; Left again from the tab wraps to the last column.
3. A is only taken while the cursor is on the Sort tab, and is handed back the moment the cursor leaves it, the bag closes, a fight starts, or the feature is switched off.
4. In a fight the game does not let addons set this up or take buttons. If the bag was already open before the fight, Left still reaches the tab but A does nothing there; use the stick click. If the bag is first opened in a fight, the d-pad route appears after the fight.

#### When it does nothing (silently, apart from one debug-log line)

- The choice is Off, or "Bag sorter" is off, or "Sort button" is set to Hide.
- The Gamepad UI is off (mouse/keyboard style has no controller cursor).
- The game is missing any of the pieces it needs (see Plan, "Guard").
- During a fight (setup is postponed until it ends).

#### Debug-log lines (module "bags")

- `d-pad: route set on N first-column slots` / `d-pad: route removed`
- `d-pad: not set up: <reason>` (reasons: `Gamepad UI off`, `no navigation helpers on this client`, `bag has no item list`, `waiting for the fight to end`)
- `d-pad: on the Sort tab` / `d-pad: left the Sort tab`
- `d-pad: A taken for Sort (A is now: <what the game says holds A>)` / `d-pad: A given back`
- `d-pad: A not taken: <reason>` (`in a fight`, `game restrictions on`)
- `Sort pressed: A on the tab`

#### What only the device can prove

1. Left from the first column lands the cursor on the tab, and the cursor is drawn sensibly beside it.
2. A on the tab sorts (i.e. our hold on A wins over the bag's), and keeps working for a second press after the bag has re-drawn.
3. After leaving the tab, A picks items up again as before.
4. **Item use is never blocked**: use / equip / sell / pick up / split from the bag, before and after visiting the tab, in and out of a fight, with no "Interface action failed" line and nothing in Settings > Errors.

---

### Risks and unknowns

1. **(Biggest) Who wins A.** Blizzard holds A with a priority override owned by `UIParent` and re-sets it on every footer refresh; ours is a priority override owned by our hidden button. The source cannot say which wins. The plan sets ours one frame after focus and again after each bag update. If it never wins, the tab can be reached but not pressed and the feature should not ship. Device-proven so far: taking a *stick* this way works out of a fight and is refused in a fight. Add to `docs/ARCHITECTURE.md` unverified table: "our A override vs the bag footer's; worst case A does nothing on the tab".
2. **Blizzard's promise that the setter leaves no taint is taken from its own comment, not from a test.** The probe only tried the setter on one of our own buttons. This is the first time a value is stored on Blizzard's item buttons at our request. If the promise is wrong, the symptom would be item use blocked after visiting the first column, until a reload. That is what device steps 2, 6, 7, 10, 12, 13 look for. There is no way for the addon to check its own write (`issecurevariable` is not in this client). Mitigation: default Off, own choice, all writes out of a fight only, frames only.
3. **Our tab becomes Blizzard's "current button".** Blizzard's bag code then reads fields from it (`buttonContext`, `isCollapsed`, `GetBagID`, cursor offsets). All are absent on our button, and every item action is fenced by `buttonContext`, so by the source nothing runs against it. A future client build that reads a method without a nil check (as `Gamepad_IsReadActionValid` does behind its fence, `ContainerFrame.lua:3181`) would raise an error inside Blizzard's footer while the tab is focused. The debug log's error page would show it.
4. **A stuck on Sort.** If the hand-back of A is refused (game restriction on while not in lockdown), A would keep going to our hidden button; the handler then does nothing unless the tab is focused, so the cost is "A does not pick items up until the bag is closed or the restriction lifts", not a wrong sort and not taint. Every sync retries the hand-back.
5. **Setter called at a bad moment prints "Interface action failed"** (device: S4/S5). Guarded by `PE:CombatRestricted()` plus `RunOutOfCombat`; the restriction can start between our check and the call only inside one frame.
6. **First-column wrap changes** (Left no longer wraps directly). Minor; stated in the spec. Bag-bar buttons that sit in the first column do not lead to the tab in v1.
7. **Cursor art**: the cursor is anchored to the left of the current button (`SmartNavigation.lua:772`); on our tab it will sit further left, outside the bag, possibly near the screen edge at large bag sizes. Cosmetic; Blizzard's custom-anchor setter exists (`SmartNavigation_SetCustomCursorAnchorPointForFrame`, `Utility.lua:169`) but needs Blizzard's `CreateAnchor` object, so leave for after the first device look.
8. **Tab hidden while focused** (choice switched from the settings window with the bag open): the cursor stays on a hidden button until the next d-pad press. We cannot move Blizzard's cursor ourselves.
9. **Value for effort.** The controller can already sort two ways with no d-pad route: the stick click (device-tested) and Blizzard's own "Clean Up Bags" entry in the bag picture's menu (`ContainerFrame.lua:735-741`). If step 4 of the device test fails, the smallest safe alternative is to do nothing new: keep touch + stick click, and say in the Bag sorter note that the game's own bag menu also has "Clean Up Bags".

## 4. Bag icons in one row at the top

### What was chosen

Approach B, small: after each of Blizzard's layout passes, move the same buttons to different cells
of the same grid. The seven bag icons go side by side in the top row, starting at the left; the
item slots follow below in the order Blizzard already had them (backpack first), with no icon
between them. Nothing is created, hidden, re-parented or resized; no item is moved.
About 130-160 new lines in `Bags.lua`, as a choice inside "Bag sorter", default "the game's way".

What it does NOT deliver:
- Items are not packed. Empty slots stay where they are until the player presses Sort. Empty slots
  still show the grey bag picture.
- It only acts in the controller style (the only style where the icons are in the grid).
- The row of icons is inside the grid's top row, not in a separate strip above the search box. The
  window keeps Blizzard's size.
- When the slot count does not fill whole rows, the short row is the first item row (under the
  icons), not the last. This is forced by the controller navigation (1.4). With some bag sizes one
  to three icons then have a gap under them.
- A bag's slots no longer sit next to its icon. Collapse (X), the bag menu (Y) and LB/RB still work
  on the icons; the hover highlight that marks one bag's slots still works.
- No window of our own, no change to which slot holds which item.

**What the player sees.** In Settings, in the "Bag sorter" row, a new choice:

- Label: `Bag icons`
- Choices: `In the grid` (default) / `One row at the top`
- Row note while it is on: `Bag icons are in one row at the top of the bag.`
- Row note if on but nothing to do: `Bag icons: only in the controller style.`

With "One row at the top": opening the bag shows the bag pictures (backpack, bags, key ring) side
by side in the top row from the left. Below them, every slot in order with nothing in between.
Switching back to "In the grid", or switching "Bag sorter" off, puts every button back where the
game had it, at once if the bag is open.

**Layout rule.** Let h = bag icons in the grid, s = slots in the grid, rows = the rows Blizzard used.
- Icons: top row, columns 1..h, in Blizzard's order.
- If the slots fit in the rows below (s <= 10 x (rows-1)): the first row under the icons holds the
  odd slots, from the left; all rows below are full.
- Otherwise (at most 10-h slots too many): those first slots finish the top row at its right end;
  all rows below are full.
- Slots keep Blizzard's order (backpack slot 1 first).

**Rules.**
- Only widget methods on Blizzard's buttons (`GetPoint`, `GetNumPoints`, `IsShown`, `IsProtected`,
  `ClearAllPoints`, `SetPoint`). No field written on any Blizzard frame or table. No Blizzard Lua
  function called. Offsets are copied exactly from what Blizzard set, never calculated, so columns
  keep identical X for the d-pad grid.
- Runs only inside the existing layout-pass hook, on the choice changing, and on switch-off.
  Nothing ticks. No new event.
- If anything is not as expected (no `GamepadBagBar`, no icon in the grid, fewer than 10 columns in
  use, a button with a different anchor than Blizzard's grid gives): do nothing, one debug line.
- Combat: allowed, the buttons are not protected. If a button says it is protected during a fight:
  leave Blizzard's layout, one debug line, redo after the fight if the bag is still open.
- Switch-off: each button gets back the exact anchor Blizzard gave it, but only if it still has the
  anchor we set. With the bag closed nothing is needed; Blizzard lays it out afresh on every opening
  (CF.lua:2857-2860).
- Bank, key ring: no bank work. The key ring icon is one of the seven and moves with them; its slots
  appear in the grid when the player expands it, as today.
- Bag size and the Sort tab are unaffected (the window's size does not change).

**Debug-log lines (key "bags").**
- `bag icons choice: row` / `bag icons choice: grid`
- `bag icons: N icons in the top row, M slots below` (only when N or M changed since the last line)
- `bag icons: left alone, no bag icons in the grid (not the controller style)`
- `bag icons: left alone, the grid is not as expected (<reason>)`
- `bag icons: held for after the fight`
- `bag icons: the game's own places put back` / `bag icons: nothing of ours to put back`

**Only the device can prove.**
- Using, equipping, selling, splitting, dragging an item is never blocked, in and out of a fight.
- The d-pad moves sensibly between the icon row and the slots, and along the icon row.
- X on an icon still collapses and expands that bag and the layout stays tidy after it.
- LB/RB still jump between icons; Y still opens the bag menu.
- It looks right at each Bag size, and after a bag is equipped or removed.

### Findings in Blizzard's source

#### 1.1 What the owner is looking at (screenshot `docs/screenshots/Screenshot_20261115-205409.png`)

The "Combined Backpack" box is 10 columns wide. In it, reading left to right, top to bottom:
a bag picture "(2)" then the backpack's slots; a red bag "(10)" then ten empty slots; a second
and third red bag "(10)", each followed by ten empty slots; a quiver picture then six stacks of
200; a bag "(1)" then its slots; a key picture in the bottom right corner. Each section is 11
cells long in a 10-wide grid, so the bag pictures step one column to the right per row: the
diagonal line. They are drawn with the same 37x37 frame as an item, so they read as items lying
in the inventory. Empty slots are drawn with a grey bag picture, which adds to the effect.

This is Blizzard's doing, not the addon's. `addons/PocketEssentials/Bags.lua` creates exactly two
frames, both children of `UIParent`: the Sort tab and a hidden 1x1 key button (`CreateButtons`,
Bags.lua:440-477). It never touches a slot.

#### 1.2 Exactly what draws the inline bag icons

- The icons are seven real buttons, children of a frame `GamepadBagBar` whose parent is
  `ContainerFrameCombinedBags`: `Blizzard_MainMenuBarBagButtons/Camelot/MainMenuBarBagButtons.xml:99-138`
  (`GamepadBackpackButton`, `Bag0SlotButton`..`Bag3SlotButton`, `ReagentBag0SlotButton`, `KeyRingButton`,
  all in `parentArray="BagButtonArray"`, template `GamepadBagSlotButtonTemplate`, 37x37, lines 25-31).
- `GamepadBagBarMixin:GetBagButton(bagID)` returns nil unless the Gamepad UI is on
  (`Blizzard_MainMenuBarBagButtons/Shared/MainMenuBarBagButtons.lua:291-299`). With mouse style the
  buttons are hidden (same file :336-338). So the inline icons exist only in the controller style.
- `ContainerFrameMixin:UpdateItemLayout` (CF.lua:1080-1106) builds one list: every item button of
  every bag that is not collapsed (:1081-1087), plus, "if combined and Gamepad UI", one bag button
  per bag (:1089-1098). It sorts the list (`SortItems`, CF.lua:993-1011: by bag, the bag's own button
  ahead of its slots, then by slot) and hands the whole list to `AnchorUtil.GridLayout` (:1103), a
  10-column grid (`GetColumns`, CF.lua:892-898) filled from the bottom right upward
  (`GetAnchorLayout`, CF.lua:984-986; start anchor `BOTTOMRIGHT` of each button to `TOPRIGHT` of
  `self.MoneyFrame`, CF.lua:3033-3035; `GridLayout` gives every button exactly one anchor point,
  `Blizzard_SharedXMLBase/AnchorUtil.lua:122-147`).
  That is why each bag's picture sits at the start of its section, and why the spare cells are at
  the top left.
- The window's height already counts the icons as cells: `GetRows` uses
  `shownSlots + NUM_CONTAINER_FRAMES` in the Gamepad UI (CF.lua:908-914).
- The "(n)" on each icon is its free-slot count (`GamepadBagSlotMixin:UpdateItemCount`,
  MainMenuBarBagButtons.lua:264-275). The grey bag picture in empty slots is a Camelot override
  (`Blizzard_UIPanels_Game/Camelot/ContainerFrame.lua:6-9`).
- Blizzard gives the icons jobs: X collapses or expands that bag's slots (`Gamepad_ToggleCollapseBag`,
  CF.lua:3346-3355; the key ring starts collapsed, MainMenuBarBagButtons.lua:341-345), Y opens that
  bag's menu, LB/RB jump from icon to icon (`Gamepad_SetCursorToBag`, CF.lua:3357-3376). So the icons
  must stay reachable; hiding them would take those away.
- Note on file loading: `Blizzard_UIPanels_Game.toc:118-124` loads `[Family]\ContainerFrame.lua`
  for game type "mainline" and `[Game]\ContainerFrame.lua` for "camelot". The Camelot file only
  overrides methods of mixins defined in the Mainline file, and the screenshot matches the Mainline
  code line for line, so both load on this client. (Inferred, not stated in the TOC.)

#### 1.3 Combined mode (approach A) is already there and already used

`ContainerFrameCombinedBags` (ContainerFrame.xml:313), CVar `combinedBags` (CF.lua:726, :2445), and
`ContainerFrameSettingsManager:IsUsingCombinedBags` returns true whenever the Gamepad UI is on
(CF.lua:2460-2468). `Bags.lua` already relies on this (`WantCombined`, Bags.lua:187-233) and adds
Sort and size. A does not fix the complaint: the complaint is about how the combined box is laid out.

#### 1.4 Can the addon re-arrange Blizzard's buttons (approach B)? Yes. What is protected:

- Nothing in the bag is a protected frame. No `protected="true"` in `ContainerFrame.xml`,
  `Blizzard_ItemButton/Shared/ItemButtonTemplate.xml`, `MainMenuBarBagButtonTemplates.xml` or the
  Camelot `MainMenuBarBagButtons.xml`. `docs/ARCHITECTURE.md:194` records the same, and the
  restriction probe found "Resize the bag: allowed" in and out of combat (ARCHITECTURE.md:271).
  So `ClearAllPoints`/`SetPoint` on item buttons and bag buttons is allowed at any time, also in a fight.
- What is protected is the act, not the frame: `C_Container.UseContainerItem` and
  `PickupContainerItem` (ContainerDocumentation.lua:584, :420, "AllowedWhenUntainted") must be reached
  by untainted Blizzard code (`ContainerFrameItemButton_OnClick`, CF.lua:1503; controller path
  `Gamepad_UseItemAction` -> `SmartNavigation:RightClick` -> `PerformClick`, CF.lua:3378-3385,
  SmartNavigation.lua:1655-1659). Taint travels through Lua values that Blizzard code later reads:
  fields we write on Blizzard tables, or Blizzard functions we call. Blizzard itself warns about one
  such field (`bagID`, CF.lua:1838-1843). Anchor points are not Lua values; moving a button does not
  taint the code that later handles its click.
- So the safe recipe is the one `Bags.lua` already follows (header, lines 6-17): write no field,
  call no Blizzard Lua function, only widget methods. Reading `bagFrame.Items`,
  `GamepadBagBar.BagButtonArray` is a read and is fine.
- When to do it: every Blizzard layout pass ends with the global `UpdateContainerFrameAnchors()`
  (after each of the five `UpdateItemLayout` calls: CF.lua:1311/1314, 2859/2860, 3040/3041,
  3093/3094, 3108/3109). `Bags.lua` already has a secure post-hook on that global
  (`hooksecurefunc`, Bags.lua:639-642, `OnLayoutPass`). No new hook is needed.
- Controller d-pad: the bag uses "grid navigation" (`SmartNavPanelInfoAdded`, CF.lua:3592-3601).
  The grid is built from where the buttons are on screen: columns are buttons with equal X, ordered
  by Y (`UpdateGrid`, SmartNavigation.lua:1332-1384), rebuilt one frame after the bag opens
  (CF.lua:2866-2873). Buttons we move are therefore found where we put them. One assumption in it
  matters: `gridHeightCompensate` (SmartNavigation.lua:1423-1426, :1456-1458) lines columns up from
  the bottom. A layout must keep every column filled from the bottom up, or left/right moves slip a
  row. This rules out "spare cells at the bottom right" and shapes the layout chosen below.
  The addon cannot change those nav settings (they sit behind `SecureHelper`, SecureHelper.lua).
- Bag opened during a fight: Blizzard lays it out as always, our hook runs, and since the buttons
  are not protected the re-flow may run then too. As a guard, if any button reports `IsProtected()`
  true during a fight, leave Blizzard's layout for that opening and redo it after the fight
  (`PE:RunOutOfCombat`, Core.lua:405), as `SyncScale` already does (Bags.lua:585-592).

#### 1.5 A window of our own (approach C): not needed

B is possible, so C was not designed. For the record: it would need its own item buttons from
`ContainerFrameItemButtonTemplate` (ContainerFrame.xml:77), its own controller navigation and
footer prompts (about 250 lines of Blizzard code, CF.lua:3387-3557, which an addon cannot reuse),
roughly 600-900 lines and high taint risk. Postpone.

#### 1.6 "Packed with no gaps" (secondary, optional)

- The game's sort exists: `C_Container.SortBags` (ContainerDocumentation.lua:554); the addon's Sort
  tab and stick click call exactly that (`DoSort`, Bags.lua:259-283). It sorts and packs, per bag
  type; a quiver's arrows stay in the quiver, bags marked "ignore" are skipped.
- Which end it packs toward is a per-character game setting: `C_Container.GetSortBagsRightToLeft` /
  `SetSortBagsRightToLeft` (ContainerDocumentation.lua:364, :513). No Blizzard Lua on this client
  calls them, so their effect here is unverified; only the device can show it.
- "Pack only, keep my order" would mean moving items one by one with `PickupContainerItem`, waiting
  on item locks between moves. Not cheap (about 150-200 lines, ticks while it runs). Left out.
- Showing filled slots first without moving items is possible with the same re-flow (order the
  buttons by "has an item"), but slots would then shift under the cursor whenever an item arrives
  or is used up. Left out; could be a later choice on top of this work.

### Risks and unknowns

- Taint (biggest). Source reading says moving unprotected buttons cannot taint item use, and the
  probe allowed resizing the bag. It has not been tried on the device for item buttons. Steps 4, 7, 8
  decide. If item use is ever blocked: the choice stays off by default and is withdrawn.
- D-pad feel. Navigation is built from positions, so it should follow. Known small oddities:
  (a) Blizzard gives the leftmost top slot an "up goes to the round bag picture" jump
  (`ApplySmartNavOverrideForLeftmostButton`, CF.lua:3559-3590), so "up" from the first slot under the
  backpack icon goes to the round picture, not the backpack icon; (b) when an icon has a gap under
  it, left/right along the icon row can drop one row at that spot. If the owner dislikes this, the
  fallback with perfect navigation is the icons in the bottom row (next to the money), which is a
  one-line change to `PlanCells`.
- After X (collapse) Blizzard re-lays out but may not rebuild its navigation grid until the bag is
  reopened (the rebuild is only in `OnShow`, CF.lua:2866-2873). This is Blizzard's behaviour with or
  without us; check step 5.
- Blizzard's layout could change in a client update (anchor shape, field names). The checks in
  `CollectGrid` then make the choice do nothing, with one debug line.
- Both ContainerFrame files loading on this client is inferred (1.2), supported by the screenshot.
- `SetSortBagsRightToLeft` is unverified in effect and not used by this design.
- Not delivered: packed items, a strip outside the grid, our own window (see part 2).

## 5. Setup guide

#### Why

Every feature starts switched off and stays that way. A new player sees a round
"PE" button and nothing else, and has to find the settings and guess what each
switch does. The setup guide walks them through the features once, in plain
words, and lets them switch on what they want as they read.

#### What the player sees

The guide is one window in the middle of the screen, the same look as the
settings window (dark box, gold edge, big buttons, the same ON / OFF switches).

- Title bar: "Pocket Essentials - Setup guide (2 of 7)" and the usual **Close**
  button at the top right.
- Body: the screen's heading, a few sentences, and under them one block per
  feature of that group: the feature's name, a big ON / OFF switch at the
  right, and two or three sentences about it. If the text is taller than the

- Bottom row, always in the same place: **Back** at the left, **Skip** next to
  it, **Next** at the far right.
  - On the first screen there is no Back, and Next reads **Start**.
  - On the last screen there is no Skip, and Next reads **Finish** (green).

A switch in the guide is the same switch as in the settings: tapping it turns
the feature on or off at once and saves it. Nothing waits for Finish. A feature
that was already on shows ON.

#### Rules

1. **When it opens by itself.** After logging in, once the loading screen is
   gone (about a second and a half after the character enters the world), if
   all of these are true:
   - neither Finish nor Skip has ever been pressed on this account;
   - the saved settings loaded properly (if they did not, the answer could not
     be remembered, so the guide stays away);
   - the character is not in a fight.
   If the character is in a fight at that moment, the guide waits and opens
   when the fight ends. It opens at most once per login this way.
2. **What stops it opening by itself.** Only **Finish** and **Skip**. They are
   remembered for the whole account (every character). The **Close** button,
   the B button, Escape, opening another Pocket Essentials window, and the game
   closing its windows by itself (loading screen, death, losing control of the
   character) all just hide the guide: it is not remembered, and the guide
   comes back at the next login. The first time this happens in a session a
   chat line says so:
   "Setup guide closed. It will show again next time you log in. Press Skip in
   it to stop that. You can open it any time from the settings."
   (Reason: Blizzard's own code closes every addon window of this kind on each
   loading screen, on death and on loss of control. If any closing counted as
   "skipped", the game could dismiss the guide before the player had read it.)
3. **Opening it by hand.** The settings window's bottom row gets a **Setup
   guide** button after "Move things". `/pe setup` does the same. Opening it
   closes the settings (only one Pocket Essentials window at a time, as today).
   It always starts at the Welcome screen. In a fight it does not open and
   says in chat: "The setup guide cannot be opened during a fight. Try again
   afterwards."
4. **A fight starts while it is open.** The guide hides at once so it is never
   in the way, and comes back at the same screen when the fight ends (unless
   the player opened another Pocket Essentials window meanwhile). This is not
   a Skip.
5. **Switches.** One source of truth: the guide's switch reads and writes
   exactly what the settings switch does. If both could be seen at once they
   would always agree. A switch shows ON, OFF, a dimmed OFF with an amber
   reason (cannot be switched on), or PROBLEM (amber: switched on but it hit an
   error), exactly as in the settings.
6. **Players who already use the addon.** Nothing they switched on is touched.
   After updating they see the guide once (they have never pressed Finish or
   Skip), and every switch shows what they already have.
7. **Screens follow the features that exist.** A feature that is not in this
   build has no block. A screen with switches but none of its features present
   is left out, and the "2 of 7" count follows.
8. **Touch and controller.** Everything is a big button. The d-pad moves the
   blue highlight (up / down by line, left / right along the reading order), A
   presses, B closes the window (as in every Pocket Essentials window). After
   Next or Back the highlight stays on the same bottom-row button, so pressing
   A repeatedly walks through the guide. Nothing is highlighted until the
   d-pad is first used.
9. **Nothing runs while it is closed.** The window is not built until it is
   first opened. It has no per-frame code at all. While it is open it listens
   for one thing (a fight starting). While closed it listens for nothing,
   except the single "fight ended" wait in rules 1 and 4.
10. **No new look, no new game functions.** Same panel, buttons, colours and
    fonts as the settings window.

### Risks and unknowns

1. **Controller keys right after login (biggest unknown).** Our windows take
   the d-pad, A and B with temporary key bindings, and "the latest one wins"
   (UI.lua:794-797). On the device the game opens its own things after every
   reload (the eighth device test saw the character pane, and once the chat
   box). If one of those takes the keys after the guide opened, the d-pad will
   not move the highlight in the guide until it is reopened; touch still
   works. The 1.5 s delay is a guess meant to let the game settle first. Only
   the device can tell. If it happens: lengthen the delay, or re-take the keys
   once shortly after opening.
2. **The game closes addon windows by itself.** Verified in Blizzard's source
   for this client: `CloseAllWindows` runs on every `PLAYER_ENTERING_WORLD`
   (`Blizzard_Game/Shared/EventImplementation.lua:305`), on death
   (`Blizzard_Game/Camelot/EventImplementation.lua:17-19`) and on loss of
   control (`UIParentPanelManager.lua:1186`), and it hides everything in
   `UISpecialFrames`, which is where `UI:CreatePanel` puts our windows. Two
   design choices follow from this and should not be "simplified" away: the
   guide opens after the entering-world event, not at login; and only Finish
   and Skip are remembered. Side effect: zoning through a loading screen with
   the guide open closes it for that session.
3. **B closes instead of going back.** The kit hard-wires B to "hide the
   window" (UI.lua:778). In a step-by-step guide a player may expect B to go
   back one screen. Keeping B = close follows the existing pattern and needs
   no change to UI.lua; because closing is not remembered, a stray B costs
   nothing lasting. Changing it would be a small addition to the kit (an
   optional per-window B handler). Question for the maintainer.
4. **Players who already use the addon get the guide once after updating.**
   That is what the request says ("no setup has been finished or skipped"),
   and it shows their current switches. If the maintainer would rather not
   show it to anyone who already has a feature on, that is a one-line rule in
   `FirstLoginCheck`.
5. **PRD wording conflict.** PRD.md ("Defaults", line 261-264) says each
   feature's default flips to on once it passes its device test. The request
   for this item says all features stay off by default and the guide is how
   they get switched on. The PRD and the CLAUDE.md convention "Features default
   off until device-tested" need rewording in the same change.
6. **Same-release merges.** Other people are adding features in this release.
   Likely conflict points: the bottom row in Settings.lua `BuildCoreSection`,
   `SlashCommand` in Core.lua, the TOC file list, the `FEATURES` lists in
   `core_test.lua` and `tests/smoke/run.lua`, and the guide's texts for Bags
   and Chat (which describe today's behaviour and will be wrong if the bag
   window or chat size feature changes it). The row keys of the new features
   are not known yet; nobody should add a row from this document's guesses.
   Whoever merges last re-reads the guide's texts against the merged code.
7. **Texts describe the controller style.** The Chat text says "press A when
   Press A to type appears", which is only true with the game's Gamepad UI on
   (Chat.lua:643-670); with it off the chat box opens at once. The Bags lead
   text likewise. This is right for a handheld and slightly off for a desktop
   player. Making texts depend on `PE:GamepadUI()` is possible later (a second
   text field per row) but was left out to keep one row = one text.
8. **Text length.** At the Large button size on a 720p screen the Chat and
   Quests screens will not fit and will scroll. The scroll area handles it,
   but the paging column takes width and the player must scroll before the
   second switch is visible. The d-pad brings a switch into view by itself.
   Worth checking on the device at Large (step 4).
9. **Text measuring.** Heights come from the game measuring wrapped text, with
   an estimate as fallback (Settings.lua:76-87). The stand-in client's
   measurement is rough, so the offline tests cannot prove nothing overlaps;
   only the device can.
10. **Existing tests assume no window opens by itself.** Handled by the
    `T.new` line in 2.8, which depends on the first-login check reading the
    saved field when its timer fires. If someone later makes the check read it
    earlier, about 100 tests start failing in confusing ways. Say so in a
    comment at both places.
11. **Switching a feature on in the guide acts at once**, exactly as in the
    settings: Big chat buttons changes what the round button does while the
    guide is still open, and Bag sorter can ask for a reload. This is by
    design (one source of truth) but is the first time a brand-new player
    meets it.
12. **Not in scope, proposed only:** choosing the button size and the round
    button's position inside the guide (today the guide only says where they
    are); a "show me" picture per feature; showing the guide again when a
    later version adds a feature. Each needs the maintainer's yes first (PRD
    rule 4).
