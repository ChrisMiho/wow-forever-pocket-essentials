# 0.22.0: the parked batch

Status: approved by the owner on 2026-11-27 ("yes, approved"). Not built yet.

Sources: `docs/11-27-morning/HANDOFF-2026-11-27.md` (the parked list and every decision of
2026-11-27, with the source lines), `docs/SCREEN-MAP.md` (where every piece sits), and the
mockup page https://claude.ai/artifact/B6emNUJNYkzyeQPghzaMAH (screens "Timers: bars on the
left", "Direction marks", "Target menu").

## Why

After 0.21.0 the owner has a list of parked fixes and ideas, and asked (2026-11-27) to build
all of them in one go instead of one release each: "build ALL of the remaining parked ideas,
feature flagging them and ensuring logs are beautiful for debugging later so we can do one big
batch test again". The owner's wider reason: alts play well on the handheld, but the main is
"a bit overwhelming figuring out where everything is with so many spells".

This sets aside the project's usual rule of one item per release. What makes that safe is in
"How the batch is made safe to test" below.

## How the batch is made safe to test

1. **Every item has its own switch, and every switch starts Off.** (The owner: "default should
   always be off".) Installing 0.22.0 changes nothing on screen until a row is turned on.
2. **All the switches are in one place:** on the Controller tab, under a new header "0.22.0",
   below everything that is already built (the owner, 2026-11-27: "the new features should
   all be under the controller tab for now, we can add a new 0.22.0 header and place new
   stuff under there to separate it from what we've already built"). One row per item in the
   order of this spec. Each row says in a few words what it does and whether it needs a
   reload. No new tab.
3. **A row "Turn all on"** right under that header sets every row of the batch On (and "Turn
   all off" sets them Off), so a test does not start with a dozen taps. It only flips the
   rows; nothing else.
4. **If something misbehaves,** turn rows Off one at a time and reload until it stops. The
   row that stopped it names the cause. (This is how the 0.16.x refused actions were found.)
5. **The debug log tells the story by itself.** At every login one line lists the state of
   every row of this batch, for example
   `batch: 0.22.0 rows: emptySlots=on arrows=on dpad=off mapStrip=on marks=on ...`.
   Each item then writes its own lines, listed under the item. Every line starts with the
   item's name, says what it did or why it did nothing, and gives the numbers it used.
   Nothing is logged while the Debug log is off, and nothing runs while an item's row is Off.

## The items

Each item: what the player gets, its row under the "0.22.0" header on the Controller tab, and its log lines.

### 1. Empty spell slots are drawn cleanly

- **Today:** an empty slot shows a grey box or a striped smear (seen on the top face button in
  `docs/11-25-evening/Screenshot_20261125-151752.png`). A new character has many empty slots:
  the mage's trigger bars were nearly all empty.
- **With the row On:** an empty slot shows only a thin, faint outline, the same in every state
  (resting, a trigger held, a targeting bar showing), with no leftover cooldown shade, glow,
  count or range dot.
- **Row:** "Empty slots, clean". No reload.
- **Log:** `empty slots: <panel> <spot>: empty because <no button | no icon shown | no texture>`
  once per slot when it changes, so the cause of today's smear is on record.

### 2. Menu arrows show for controller players too

- **Today:** the scroll arrows at the side of a long menu show only for touch players.
- **With the row On:** they always show when a menu is longer than its window, as the sign that
  it goes on. Tapping them still works; a controller scrolls as it does today.
- **Row:** "Menu arrows, always". No reload.
- **Log:** `menu arrows: shown (list <n> rows, window fits <m>)` when a window opens.

### 3. The D-pad moves to the nearest button in that direction

- **Today:** D-pad Left and Right walk the buttons in list order, so in windows such as Arrange
  the highlight seems to circle around.
- **With the row On:** in every PE window, a D-pad press moves to the nearest button in the
  pressed direction. If there is none that way, the highlight stays where it is. Windows that
  already have their own rule (the settings tabs, the setup guide) keep it.
- **Row:** "D-pad moves by direction". No reload.
- **Log:** `dpad: <direction> from "<button>" to "<button>"` or `dpad: <direction>: nothing that way`.

### 4. The square map's name strip is tidy

- **Today:** the place name is cut ("Powderfuse Po"), the game's day-and-night sun sits on top
  of it, and a "?" mark (the game's controller button holder) hangs off the map's left edge.
- **With the row On:** the whole place name shows, shortened with "..." only when it is wider
  than the map; the sun sits in the top right corner clear of the name; the "?" holder is put
  inside the map's edge or hidden if it cannot be.
- **Row:** "Map name strip, tidy". Needs Map look: Square. No reload.
- **Log:** the existing `map look: rim:` lines, plus `map strip: name "<text>" fits | cut at <n>`
  and `map strip: <mark> moved to <spot> | hidden | left alone because <reason>`.

### 5. Bigger direction marks on the spell pictures

- **Today:** a small mark of four dots; the d-pad and the face buttons differ by one faint dot.
- **With the row On (mockup "Direction marks", Option A, the owner's pick):** a solid cross in
  a square means d-pad, four round buttons in a circle mean face buttons, and the pressed
  part is gold. About 24 units across on a 42-unit picture, in the same corner as today.
- **Row:** "Bigger direction marks". No reload.
- **Log:** `marks: bigger marks drawn on <n> pictures (size <units>)`.

### 6. The target's menu opens above the tooltip corner

- **Today:** pressing Inspect with a target opens the game's menu for that target (Interact
  With Target, Target Marker Icon, Set Focus, Edit Mode) in the bottom right, over the
  tooltip. The game pins that menu to its own target frame, which is invisible while Slim
  bars are on but still sits where our layout puts it.
- **With the row On (mockup "Target menu"):** our layout puts that invisible frame higher, so
  the menu opens at the same right edge, above the tooltip and the target-of-target bar.
  Nothing visible moves except where the menu appears.
- **Row:** "Target menu above the tooltip". Needs Slim bars On. Needs a reload.
- **Costs, stated plainly:** the invisible frame has a guard over it that swallows taps. It
  moves up with the frame, into the right side of the play area, which matters to players
  who tap the world there. A longer menu (a player target has more entries) or a very long
  quest list can still meet it.
- **Log:** `target menu: the game's target frame written at <x>, <y> (was <x>, <y>)`.

### 7. Arrange covers more of the screen

- **Today:** Arrange offers the pieces our layout places. The game's own cast bar and its focus
  frame are not ours and cannot be moved there; the focus frame's box sits over the quest
  list.
- **With the row On:** both become pieces of our layout at the spots the game gives them today
  (so nothing moves at first), and Arrange lists them. The timer pieces of item 8 are listed
  too when that row is On.
- **Row:** "Arrange: cast bar and focus frame". Needs Arrange it yourself On. Needs a reload.
- **Not in this item:** a choice of whole starting arrangements (for example the map in a top
  corner). That is a second complete arrangement and waits for a later round.
- **Log:** `arrange: <piece> joined the layout at <x>, <y>`.

### 8. The game's timers get a place (the Cooldown Manager)

- **Today:** with the game's timers switched on, two rows of icons cover the map and the buff
  bar lies across the quest list, because our layout has no place for them.
- **With the row On (mockup "Timers: bars on the left"):**
  - **Timer icons** go to the bottom left corner, under your slim bar: one row of up to six
    large icons with the small ones under it, at 80% size. A seventh large icon starts a
    second row above the first; that room is kept free.
  - **Buff timer bars** stack above your slim bars and grow upward, at 80% size and standard
    width. Three fit; the chat ends a little higher to make room. A fourth lands on the
    chat's lowest lines, and the player adjusts from there.
  - **Tracked buff icons** sit in a row beside the bars.
  - **The PE button** moves to the left of your slim bars, with a gap to them and a full
    button's width in from the screen's edge (the owner's rule: never hugging the edge, where
    a hand holding the device can touch it). A button the player has moved is put at the new
    spot once, when this row is first turned on, and can be moved again.
- **Row:** "Place the game's timers". Needs a reload.
- **Second row:** "Buff timer bars: Left, by your name / Right, by the target". Right is the
  first mockup: the column above the target bar instead. Needs a reload.
- **We set the game's own pieces through our layout only** (their spot, icon size, icons per
  row, bar width). We do not draw timers ourselves and do not switch the game's timers on or
  off: that stays the player's setting.
- **The sizes are a first try.** They are written to the log so that after the test we change
  numbers instead of guessing.
- **Log:** `timers: <piece> written at <x>, <y>, size <n>%, <k> per row` for each of the four
  pieces, `timers: bars on the <left | right>`, `timers: chat ends at <y> (was <y>)`,
  `timers: PE button at <x>, <y> (was <x>, <y>)`, and `timers: the game's timers are switched
  <on | off>` so a test with them off is not mistaken for a fault.

### 9. One layout per character, named after the character

- **Today:** one layout called "Pocket Essentials" is shared by every character of the account.
  Arranging the screen on one character changes it for all of them.
- **With the row On:** each character that uses Controller layout gets its own layout, named
  **"First Last -PE"** (for example "Forgot Shards -PE"): the whole name, first name and
  surname, then the tag, one pattern for every character. If a name is ever too long for the
  game's 30 letters, the first name is shortened and the surname stays whole.
- **The player's own layouts are never changed,** as today. The addon writes only its own
  layout and remembers which one the character had before; turning Controller layout off
  puts that one back.
- **A note for the player,** on the Controller tab and once in chat when the layout is first
  made: "Pocket Essentials uses its own screen layout for this character. Your own layouts
  are not changed. Turning Controller layout off puts back the one you had."
- **Every new layout starts from the same default setup** (the owner, 2026-11-27: "there
  should be a default setup that every new profile gets"). That default is the addon's
  built-in arrangement, the one in `docs/SCREEN-MAP.md`, plus whatever rows of this batch are
  On. A character's layout is built fresh from it; nothing is copied from another character
  or from the old shared layout.
- **The shared layout that exists today** ("Pocket Essentials") is no longer used while this
  row is On. It is left in place and never written again; the note says it can be deleted in
  Edit Mode. The owner accepts losing what was arranged in it ("given this is a dev process,
  its okay if we lose the PE profile"); the arrangement of the first device sitting is
  already part of the default.
- **Arranged positions** are saved per character while this row is On, starting empty, so
  each character's own moves belong to its own layout. Positions saved for the whole account
  before are kept untouched for when the row is Off.
- **If the character already has five layouts of its own** (the game's limit), the addon makes
  nothing, keeps using the shared layout, and says so on the Controller tab.
- **Row:** "A layout for each character". Needs a reload.
- **Not verified yet:** that the game accepts a character layout saved by an addon. If it does
  not, this item is taken out of the build and reported, not worked around.
- **Log:** `layout: active at login "<name>" (<kind>)` at every login whatever the row says,
  `layout: made "<name>" for this character, copied from "<name>"`,
  `layout: five layouts already, nothing made`.

### 10. Spell panels at 110% and 120% are not cut off

- **Today:** with Spell panel size 110% or 120% and Arrange Off, the lowest spell button is cut
  by the screen's edge.
- **With the row On:** the panels sit high enough at every size that no button is cut.
- **Row:** "Large spell panels, whole". No reload.
- **Log:** `panels: size <n>%, lowest button's bottom at <y>`.

### 11. "Map buttons" says when it does nothing

- **Found while planning (2026-11-27): this is already built.** Since 0.19.0 the row reads
  "Map buttons: Round map only" while Map look is Square (`ControllerLayout.lua`, the
  `mapButtons` row). So there is nothing to build and no row for it. (Making the place name
  and the clock open something on the square map is not in this batch: it needs a decision
  on what they should open.) The item's number is kept so the others do not shift.

### 12. The mount square keeps itself up to date

- **Today:** the mount square in the PE window does not refresh while the window stays open
  (mounted, in a fight, indoors).
- **With the row On:** it redraws when any of those change while the window is open.
- **Row:** "Mount square, live". No reload.
- **Log:** `quick slots: mount square redrawn: <mounted | in a fight | cannot mount here | ready>`.

## Not in this batch

- The target's and the pet's buff and debuff boxes (still waiting for the probe's "Buffs in a
  fight" run). Their rooms stay reserved.
- A second starting arrangement (the map in a top corner).
- Anything that asks which device this is, or that changes game settings.
- Getting off a mount in a fight; more quick slots.
- Per-character switches for the rest of the addon, the performance fixes, the Controller tab
  clean-up.
- Drawing timers, bars or buffs ourselves.

## What would make it a failure

- Anything on screen changing after the update while every row is Off.
- A refused action, or anything that stops spells casting, with any mix of rows.
- A row that does nothing and says nothing in the log.
- One of the player's own layouts changed or lost.
- A row that cannot be undone by turning it Off (and reloading where it says so).

## Rules for the build

- Verify every game call in the pinned source and cite file and line; log the ones that
  cannot be verified in `docs/ARCHITECTURE.md` with their worst case.
- Never call a Blizzard function that writes a field or a global, never set a field on a game
  frame, never move, scale or hide an Edit Mode piece directly: the layout is the only way.
- Handlers go through `PE:Safe` or `PE:Wrap`. Nothing ticks while its row is Off.
- `ControllerLayout.lua` is near Lua's limit of 200 locals: new numbers go on tables.
