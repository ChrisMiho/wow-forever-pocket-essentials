# 0.20.0: after the first sitting (names, the owner's arrangement, the Part rows, the wheel buttons)

Status: **approved 2026-11-25** by the owner's "do the one build with the map, and just
follow it up with a second build for everything else", said while away at work (an away
batch: built, reviewed and published as a pre-release with nobody to ask). The items are the
owner's requests after the first device sitting of 0.18.0 (2026-11-25), quoted below in
their words. Built on top of 0.19.0.

Blizzard's source is `~/.cache/wow-ui-source/forever` at `c01a87b`, build 1.60.1 (71091);
paths below are under `Interface/AddOns/`. The rules of ARCHITECTURE "Calls into Blizzard's
Lua" apply to every part.

## 1. Whole names on the slim bars

"only the first name on the bars, would like the second name too, or the ability to toggle
which id like". The 2026-11-25 screenshots show "41 Forgot" for the character "Forgot
Shards" on a 280-wide bar with room to spare: the second name is not cut, it is never read.
`SlimBars.lua:357-360` shows only the first answer of `UnitName`. On this client the game
joins a first name and a surname itself (`Blizzard_UnitFrame/Mainline/UnitFrame.lua:145-163`,
`Blizzard_UnitPopup/Mainline/UnitPopupUtils.lua:122-131`,
`Constants.CharacterNameSeparatorConsts.CHARACTERNAME_SURNAME_SEPARATOR`).

- A row on the Controller tab, **Names on the bars**: `Whole name` (the default) /
  `First name`. Stored as `opts.slimNames` (1 / 0). It applies at once, no reload.
- Whole name: the first name, the game's surname separator, the surname, when the unit has
  one. The builder reads how the game tells a surname from a realm name (the files above and
  `NameUtil`) and makes the same engine calls; it does not call the game's Lua helpers. A
  realm name is never shown.
- A name wider than its room is cut with "..." at the room it has today (the level and the
  health number keep their places). The pet and target of target bars (136 wide) cut sooner.
- If the second answer is hidden in a fight (`UnitName` is marked
  `SecretWhenUnitNameIdentityRestricted`, `UnitDocumentation.lua:2489`), the bar keeps the
  name it had; nothing is joined to a hidden value.
- Log: `slim bars: names: whole / first` at start and on change; once per session the first
  time a surname is joined (`a surname was joined for the player bar`) or could not be read.

## 2. The owner's arrangement becomes the built-in one

"there are so many pieces to move, isnt there a better default version?" Promised: their
arrangement becomes the built-in one. From the last Apply and the next login in the saved
file of 2026-11-25 (lines `arrange: apply:` at 14:45:14 and `arrange: offset:` at 14:45:30):

| Piece | Saved offset (x, y) |
|---|---|
| map | 0, -2 (not folded in, see below) |
| buffs and debuffs | 0, 4 |
| inner left / inner right diamond | 0, -16 |
| outer left / outer right diamond | 0, -16 |
| LB targeting picture / RB targeting picture | 94, -56 / -94, -56 |
| player bar / target bar (slim) | -18, -16 / 18, -16 |

Everything else was at 0, 0.

- `Plan`'s built-in spots take these amounts, in one table (`Plan.BASE_2 = { [piece] = { x, y } }`)
  added where the session's offsets are added, so the twins stay exact mirrors by
  construction and the numbers above are in one place.
- **The map is left out of the table.** 0.19.0's build found that the game holds an Edit Mode
  piece on the screen (`Blizzard_EditMode/Shared/EditModeSystemTemplates.xml:4`), so the
  saved "map 0,-2" below the bottom edge does nothing in the game. It is not folded in and
  the saved offset is left as it is. The square map keeps its own box (x -100..100,
  y 4..204).
- **The square map's warning goes.** 0.19.0 reports three overlapping pairs for Square with
  Slim bars On and nothing moved (its as-built note 4), because the targeting pictures' 20
  outwards was drawn on top of this arrangement. With the arrangement built in, Square with
  nothing moved must give 0 overlaps at 80%, 90% and 100%, and the status line
  "With the square map 3 pairs of pieces overlap..." is only shown when the check really
  finds a pair.
- **Nobody's screen moves twice.** Saved data gains a mark, `arrangeBase` (per layout options
  for the Edit Mode pieces, per character for the live ones; absent means 1). At the first
  load with a mark below 2, each saved offset has its piece's amount subtracted, the
  written-offsets record (`Plan.MarkWritten`) is adjusted the same way, and the mark is set
  to 2. Built-in plus offset is then exactly what it was: the owner's offsets all read 0,
  and someone with other offsets keeps their screen to the unit. A character that logs in
  later migrates its own live offsets then.
- With **Arrange it yourself Off** nothing was offset, so the screen does take the new
  spots: the live pieces at the next placement, the one Edit Mode piece (buffs and debuffs) by
  the layout being written again with the usual reload prompt. The CHANGELOG says so.
- "Start over" in the Arrange window now returns to this arrangement.
- `Plan.Overlaps` is 0 with the new built-in spots for Round and Square, slim On and Off,
  at each Spell panel size that had 0 before; a size that newly overlaps is named in the
  as-built notes and the row's status line reports it, as today.
- Log: `arrange: built-in arrangement 2`; on a migration, one line per piece changed
  (`arrange: moved into the built-in spots: player bar -18,-16 -> 0,0`).

## 3. The Part rows are removed

The seven "Part: ..." rows were for finding the refused actions of 0.16.0 to 0.16.2. They
kept Off values from that hunt and hid the split spell panels until set back.

- The six part rows and `Plan.TEST_PARTS` go; every part is always placed. Saved `tHints`,
  `tChat`, `tMap`, `tBars`, `tExtras`, `tFace` values are ignored and cleared at load.
- The seventh row, "Part: follow the triggers with a hook" (`tHook`), goes too, with the
  hook path it switched on: it was never tried on a device, and the game's callback list
  that the addon uses instead is device-proven. Its ARCHITECTURE row is removed.
- The log line `bars placed (parts left out: ...)` becomes `bars placed`.
- If refused actions come back, the method stays documented (ARCHITECTURE, "A refusal's
  call stack..."); rows can be added again for the hunt.

## 4. The spell wheel buttons can be moved without a second switch

"i couldnt move the icons that host the spells of the pets". The screenshots confirm they
are the two round buttons above "LB + LT" and "RB + RT"; they stayed put because
"Arrange: spell wheels" was Off.

- The row "Arrange: spell wheels" goes. With Arrange it yourself On, the piece
  "Spell wheels and their buttons" is always in the Arrange window. It still moves up and
  down only, both sides together (the game re-anchors them sideways itself; 0.18.0 spec).
  The window says so on that piece: `Up and down only. Both sides move together.`
- With its offset at 0, 0 nothing is done to the game's bottom anchor that 0.18.0 with the
  switch Off did not do: the test compares the calls made.
- A saved `arrangeWheel` is ignored and cleared; an offset saved while it was On is kept.
- Still unproven on a device (the ARCHITECTURE row stays): that the wheels open where the
  buttons are after the move.

## As built

Built on 2026-11-25 in five commits on `playing-screen-0.17.0`, on top of 0.19.0 (the plan's
Tasks 1 to 5: `5189892` names, `104cc99` the Part rows, `0113c0d` the wheel buttons, `eb44e48`
the arrangement, then the documents). Offline: `scripts/check.sh`, `scripts/test.sh` (1,122
feature tests; 1,101 before), `scripts/audit-api.sh` and `scripts/build.sh` exit 0. The taint
check has no new line and one fewer (`SetActiveActionBar`, the hook that went); no kept call
was added. Not yet tested on a device. Where the build departs from the text above, and why:

### 1. Names

1. **What `UnitName`'s second answer is.** Blizzard's source has no call that returns a surname
   alone, and documents the second answer only as "unitServer"
   (`Blizzard_APIDocumentationGenerated/UnitDocumentation.lua:2489-2503`). This client's own
   helper treats any second answer as a surname and joins it
   (`Blizzard_FrameXMLUtil/Camelot/NameUtil.lua:4-12`, the file this client loads:
   `Blizzard_FrameXMLUtil.toc:58-59`). The code shared with the other clients tells the two
   apart with `RegionalUniqueNamesEnabled()` (`Blizzard_UnitPopup/Mainline/UnitPopupUtils.lua:126-131`:
   true, a surname; else a realm's name unless the unit is on the player's realm). The build
   takes the stricter of the two: the second answer is joined **only while
   `RegionalUniqueNamesEnabled()` is plainly `true`**. So a realm's name can never show, at the
   price that the bars keep first names if that function says no on the device (the debug log
   then says so, once). It is an engine function (`UnitDocumentation.lua:536`), called through
   `pcall`; `GetUnitName` and `NameUtil` are not called.
2. **`C_PlayerInfo.ShouldDisplaySurname` is not asked.** The game's own player frame hides the
   player's surname when it says no (`Blizzard_UnitFrame/Mainline/UnitFrame.lua:155`). The row
   "Names on the bars" is the choice here.
3. **A hidden second answer.** "The bar keeps the name it had" is done only where that is
   right: while the bar already shows a whole name for the same unit. A bar whose unit may
   have changed (a new target, a new target of target, a new pet) would keep another unit's
   name, so there the first name goes into the widget as it came, alone, as up to 0.19.0.
   Nothing is ever joined to a hidden value.
4. **The cut.** A plain name is measured with the font string's own `GetUnboundedStringWidth`
   and shortened with "..." on whole characters until it fits the room the bar had (170 on a
   main bar, 126 on a small one). A hidden name cannot be measured; the font string is one
   line wide and cuts it itself.
5. **The separator's value is not in the source** (an engine constant; a comment at
   `Blizzard_ChatFrameBase/Shared/SlashCommands.lua:1163` says it is a space). It is read
   through `pcall`, with one space as the fallback.
6. **The log line for a surname** is written once a session, for the first bar that joins one
   (`a surname was joined for the player bar`), not once per bar.

### 3. The Part rows

7. **ARCHITECTURE had no "A refusal's call stack..." paragraph.** The spec points at one; it
   is written now (under "Calls into Blizzard's Lua"), with the method of 0.16.2.
8. `Plan.TEST_PARTS` is replaced by `Plan.GONE`, the seven saved keys removed at load.
   `PE.FaceBars:Start` no longer takes a third argument; one passed is ignored.

### 4. The wheel buttons

9. **A second saved value was needed.** The switch was the account's and the offset is each
   character's, so "an offset saved while it was On is kept" cannot be decided from the
   account's file once `arrangeWheel` is cleared. The account's file keeps what the switch was
   (`opts.wheelWas`, 1 or 0) and each character's file is marked when it has been dealt with
   (`ctrlArrange.wheel = 1`). `arrangeWheel` itself is gone after the first load.
10. **The window's note stands in for "Moves as you press."** on that piece: the line has no
    room for both at 720p by the stand-in's letter widths. `Arrange:Changed`, which only the
    removed row called, is removed.

### 2. The arrangement

11. **`Plan.MigrateBase(store, mark, kind, everyPiece)`** has two more arguments than the plan
    gives it: the kind of piece (the account's store holds the Edit Mode pieces, a character's
    the live ones) and whether pieces with nothing saved are done too.
12. **With Arrange it yourself On, a piece with no saved offset gets minus its amount.** It
    stood at the old built-in spot, and "someone with other offsets keeps their screen to the
    unit" needs it to stay there. The plan's example (`player bar -10,0` gives `8,16`) is one
    piece; the rest of that character's pieces then read "Moved 16 up" and so on, and "Reset
    all" goes to the new arrangement. With the switch **Off** the offsets were not in use: only
    entries that are saved are changed, and the screen takes the new spots.
13. **A character with nothing saved for Arrange** (no `ctrlArrange` table: not played with the
    switch On since 0.18.0) has nothing to carry over and gets the new spots.
14. **The written-offsets record is not adjusted; its meaning is.** `opts.offsetsWritten` now
    holds each Edit Mode piece's whole distance from arrangement 1's spot (built-in amount
    plus offset), which is what the layout holds. Carrying over changes offset and amount by
    the same number, so the record stays true as it is: nothing waits and no reload is asked
    for. The same record does the other case with no extra mark: with the switch Off, a layout
    written before 0.20.0 has nothing noted for the buffs, so that piece waits and is written
    once (the path that already wrote moved pieces back when the switch is Off), with the
    reload asked for and the chat line "The controller layout has a new built-in arrangement.
    Open the settings and tap Reload now to finish." A layout built from an older template is
    left for its rebuild at the next login. A move of the buffs made by hand in Edit Mode is
    replaced by that write.
15. **"Start over" in the Arrange window** is its "Reset" and "Reset all": both go to the new
    arrangement because an offset of 0, 0 now means it. (The row "Rebuild the layout / Start
    over" rebuilds the Edit Mode layout with the offsets, as before.)
16. **`Plan.Overlaps` at each Spell panel size.** 80%, 90% and 100%: 0 pairs, Round and Square,
    Slim bars On and Off, hint box and map buttons shown or not. **110% and 120% newly
    overlap** (they had 0 with nothing moved): the arrangement was made at 100%, and the
    larger spell panels, 16 lower, meet the LB and RB targeting pictures (two pairs: 17 by 4.9
    and 17 by 9.8 with the round map, 36 wide with the square one) and reach 3.9 and 8.8 under
    the screen's bottom edge. 0.19.0's as-built note 4 said the same of this arrangement as
    saved offsets. The card reports it: the status line is no longer for the square map only
    ("2 pairs of pieces overlap. Arrange the screen shows which, and moves them."; with Square
    it begins "With the square map"), and it counts as the Arrange window does (the rooms kept
    for the buff boxes are not pieces).
17. **Two smaller meetings at 100%, not counted by `Plan.Overlaps`** (neither is a piece of the
    plan). The frame of ours under each inner spell panel that takes a tap reaches 4 units
    under its side's targeting picture (21 by 4; it draws nothing and the picture takes no
    tap), as it has on the device since the pieces were arranged so. And if the spell pictures
    are ever off, the game's own upper bar on each side, shown at full size, meets the picture
    4 wide. Tests name both.
18. **`arrange: built-in arrangement 2` is logged in every session** that places the layout,
    also with Arrange it yourself Off.
19. `FaceBars.lua`'s own copies of the panels' and real bars' spots (used only if the plan's
    are missing) are 16 lower too.
20. **The stand-in client's Gamepad preset had no buffs or debuffs**, so no test could see
    that piece written. It has the two now, at the real preset's spots
    (`Blizzard_EditMode/Mainline/EditModePresetLayouts.lua:433-467, 1402`).

### What only the device can show

  is true (ARCHITECTURE, "Unverified API").
- That the spell wheels open where their buttons are after the piece is moved (unchanged
  from 0.18.0; now reachable without the second switch).
- That nothing moves at the first login with the saved file of 2026-11-25. The tests use
  tables shaped as 0.19.0 wrote them, with that file's offsets.

### After the review (2026-11-25)

A second reader traced the carry-over by hand for the owner's saved data, a second character,
Arrange Off, Arrange switched On later, and Reset, and checked the names against Blizzard's
source. Nothing blocking. Changed after it:

- **Names: any second answer is joined, and `RegionalUniqueNamesEnabled()` is no longer
  asked** (this replaces as-built note 1's "stricter" rule and the spec's "a realm name is
  never shown"). The game's own unit frames on this client do exactly that
  (`GetUnitName`, `Blizzard_UnitFrame/Mainline/UnitFrame.lua:1094-1096`, is
  `NameUtil.FormatUnitNameForDisplay`, `Blizzard_FrameXMLUtil/Camelot/NameUtil.lua:4-12`),
  and the device showed "Forgot Shards" on the game's player frame. The stricter rule risked
  a build in which the one thing asked for did not happen. Not known off the device: what
  the second answer is for creatures, pets and other players; the bars will show what the
  game's frames would.
- **The mark is set before the log lines are written**, so a carry-over can never run twice.
- **A character with Arrange it yourself On that never moved a live piece takes the new
  arrangement** (this replaces as-built note 12 for the live pieces). The Edit Mode pieces
  keep the builder's rule: with the switch On they stay where the layout holds them.

Left as built, for after the device test: at Spell panel size 110% and 120% the new
arrangement puts the panels' lowest button 3.9 and 8.8 under the screen's bottom edge when
Arrange it yourself is Off (the arrangement was made at 100%). The fix is known (the
panels' 16 down limited by the panel's height) but changes the carry-over's sums, so it
waits. Going back to 0.19.0 and forward again moves the pieces: do not install 0.19.0 over
a file 0.20.0 has saved.
