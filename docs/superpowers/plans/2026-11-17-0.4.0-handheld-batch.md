# 0.4.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. One task at a time, in the order given.

**Goal:** chat text size stepper, a background for pop-up menus, d-pad reach for the bag Sort tab, equipped-bag icons in one row at the top of the bag, and a first-run setup guide.

**Architecture:** each task is one module or one choice inside an existing module, following the patterns already in `addons/PocketEssentials`. Tasks 3 and 4 both change `Bags.lua`; task 5 (`Setup.lua`) comes last so its screens can name the modules the earlier tasks registered.

**Tech Stack:** Lua 5.1 for the client, LuaJIT offline tests with the stand-in client in `tests/lib/fakeclient.lua`.

**Spec:** `docs/superpowers/specs/2026-11-17-0.4.0-handheld-batch.md` (its "Rulings" section wins over any task text).

## Global Constraints

- No libraries. Event handlers and callbacks go through `PE:Safe` or `PE:Wrap`.
- Nothing ticks while its feature is off. Every new feature or choice starts off / on today's behaviour.
- Using an item from the bags must never be blocked: no Blizzard function is replaced, nothing is written onto Blizzard frames except through the setters named in the task.
- Every new Blizzard name is verified in `~/.cache/wow-ui-source/forever`; run `scripts/audit-api.sh` after adding one; names it cannot see go in `tests/api/extract.lua` `INDIRECT`; unverifiable ones get a row in `docs/ARCHITECTURE.md`.
- `scripts/check.sh` and `scripts/test.sh` pass at every commit (check has a wording check on comments).
- Each task adds its numbered device steps to `docs/TESTING.md` and its lines to `CHANGELOG.md` under `[0.4.0]`. The last task sets the TOC version to 0.4.0 and updates PRD.md, README.md and docs/DECISIONS.md.

## Review Focus

- Item use (press, drag, sell, split) with each new bag choice on, in and out of a fight.
- A bag opened during a fight with "Bag icons" or "D-pad to Sort" on.
- Switching each new choice off gives back exactly the game's layout and bindings.
- The setup guide never opens in a fight and never opens again after Finish or Skip.
- A menu that closes or is reused never leaves our background panel on screen.

##### 3.3 Functions in `MenuBackground.lua` (decisions, not code)

File-local state: `panels` (array of our frames), `byMenu` (menu frame -> panel, plain table, entries removed on release), `listening` (bool), `questHooked` (bool, the hook cannot be removed so it is installed once and checks `mod:IsEnabled()`), `watching` (bool), `shownCount`, `saidBoth` (bool).

Constants: `OUT_X = 6`, `OUT_Y = 3`, `FILL = {0.05, 0.05, 0.05, 0.95}`, `EDGE = {0.52, 0.52, 0.57, 1}`, `MAX_PANELS = 6`, `ART = "common-dropdown-bg"`, `QUEST_FN = "QuestMapLogTitleButton_CreateContextMenu"`, `EV_SHOW = "MenuProxy.OnShow"`, `EV_HIDE = "MenuProxy.OnHide"`, `EV_CLOSE = "MenuProxy.OnClose"`.

1. `local function IsMenuFrame(menu) -> boolean`
   True only for a table with function fields `GetFrameLevel`, `GetFrameStrata`, `IsShown`, and for which `menu:IsForbidden()` is not true. Anything else is skipped (log `menu skipped: forbidden` for the forbidden case).

2. `local function NewPanel() -> frame`
   `CreateFrame("Frame")` with **no name and no parent** (reason in 1.5; the menu frames are parentless too, `Menu.lua:2187`). `EnableMouse(false)`. Two textures made by us: `edge = f:CreateTexture(nil, "BACKGROUND")`, `SetAllPoints()`, `SetColorTexture(EDGE)`; `fill = f:CreateTexture(nil, "BORDER")`, inset 1 on each side, `SetColorTexture(FILL)`. Same construction as `QuestIcons.lua:310-316`. Starts hidden.

3. `local function AcquirePanel() -> frame or nil`
   First hidden panel in `panels`; else a new one if `#panels < MAX_PANELS`; else nil (log `no room`).

4. `local function Attach(menu, path) -> boolean`
   `path` is `"announcement"` or `"quest hook"`.
   - `Sweep()` first (see 7).
   - If `byMenu[menu]` exists: re-apply strata and level (the frame is pooled and may be reused at another level), return true without a new log line.
   - `IsMenuFrame`, `AcquirePanel`; on failure return false.
   - `panel:ClearAllPoints()`; `panel:SetPoint("TOPLEFT", menu, "TOPLEFT", -OUT_X, OUT_Y)`; `panel:SetPoint("BOTTOMRIGHT", menu, "BOTTOMRIGHT", OUT_X, -OUT_Y)`.
   - `panel:SetFrameStrata(menu:GetFrameStrata())`; `panel:SetFrameLevel(math.max(0, menu:GetFrameLevel() - 1))`.
   - `panel:Show()`; `byMenu[menu] = panel`; `panel.peMenu = menu` (a field on **our** frame, never on theirs).
   - Log the `panel shown (<path>)` line (size from `menu:GetWidth()/GetHeight()`, rounded; guard with `PE.Plain` as other files do for values that may be unreadable).

5. `local function Release(menu, why)`
   If `byMenu[menu]`: hide the panel, `ClearAllPoints()`, clear both links, log `panel hidden (<why>)`.

6. `local function ReleaseAll(why)` - every panel in use.

7. `local function Sweep()`
   For each menu in `byMenu`: if `not menu:IsShown()` then `Release(menu, "menu gone")`. Runs at every `Attach`, so a missed closing announcement can never leave more than one stale panel, and that one is removed the next time any menu opens.

8. `local function OnMenuShown(_, menu)`, `OnMenuHidden(_, menu)`, `OnMenuClosed(_, menu)`
   EventRegistry calls a callback registered with an owner as `func(owner, ...)` (`CallbackRegistry.lua:207-213`), hence the ignored first argument. They call `Attach(menu, "announcement")`, `Release(menu, "hidden")`, `Release(menu, "closed")`. All three are registered wrapped: `mod:Wrap(OnMenuShown)`.

9. `local function OnQuestMenu()` - the fallback, the `hooksecurefunc` body (wrapped with `mod:Wrap`).
   - Return at once unless `menuBg:IsEnabled()`.
   - `local manager = Menu.GetManager()` and `local menu = manager:GetOpenMenu()` (each guarded by `type(...) == "function"`, called through `pcall`).
   - No menu: log `quest hook ran but no open menu was found`.
   - `byMenu[menu]` already set: log `quest menu opened, panel already there` once (`saidBoth`), return.
   - Otherwise `Attach(menu, "quest hook")`, then `StartWatch()`.

10. `local function StartWatch()` - only ever started by the fallback path.
    If not `watching`: set it and `mod:After(0.25, Tick)`. `Tick` runs `Sweep()`; if any panel is still in use and the feature is on, schedule itself again; otherwise clear `watching`. This is the only timer, it exists only while a fallback-attached panel is on screen, and Core cancels it on switch-off (`Core.lua:654`, `offCount`). On the main path nothing ticks at all.

11. `local function OnEnable(mod)`
    - Log the art line: `C_Texture.GetAtlasInfo(ART)` through `pcall`, exactly like `Bags.lua:460-463` (`missing` = call worked and returned no table; `cannot tell` = function absent or the call failed).
    - Main path: if `type(EventRegistry) == "table"` and `RegisterCallback`/`UnregisterCallback` are functions: `EventRegistry:RegisterCallback(EV_SHOW, wrappedShown, mod)`, same for `EV_HIDE` and `EV_CLOSE`, each inside `pcall`. The owner argument is the module table (`mod`); a number is not allowed (`CallbackRegistry.lua:120-122`). Set `listening`.
    - Fallback: if not `questHooked` and `type(hooksecurefunc) == "function"` and `type(_G[QUEST_FN]) == "function"`: `hooksecurefunc(QUEST_FN, wrappedQuestMenu)`; set `questHooked`. Same pattern as `Bags.lua:639-641`. If the function is not there yet (the world map addon loads on demand on some clients), try once more from `OnMenuShown`'s first call; do not poll.
    - Log the `listening:` line. If neither path is available, log the `cannot listen` line. Return normally in all cases.
    - A menu that is already open when the switch is turned on gets no panel until it is opened again (the settings page is what is open at that moment, so this cannot matter).

12. `local function OnDisable()`
    `EventRegistry:UnregisterCallback(EV_SHOW, menuBg)` and the other two (inside `pcall`, only if `listening`); `ReleaseAll("switched off")`; log the count line if `shownCount > 20`; reset `shownCount`, `saidBoth`, `watching`, `listening`. Panels are kept hidden for reuse.

### Task 3: D-pad to the Sort tab

##### How Blizzard's bag navigation works here (what the design leans on)

- `Blizzard_GamepadSmartNavigation/SmartNavigation.lua`: one global cursor object `SmartNavigation`. It binds d-pad / A / B itself (`SetupInputBindings`, l.217) and moves between the *focused window's* buttons, which it collects by walking that window's children (`Utility.FindButtons`, `Utility.lua:279`). Our tab is a child of `UIParent`, so it is never collected. That stays.
- The combined bag uses grid navigation with wrapping (`ContainerFrame.lua:3592` `SmartNavPanelInfoAdded`).
- Before the grid is consulted, `Navigate` (`SmartNavigation.lua:1472`, override block l.1503-1530) looks for a per-button, per-direction **jump override** on the current button. If it is a frame that is visible with a valid rect, the cursor goes there, **whether or not that frame is in the window's button list**.
- Blizzard's own precedent in the same window: the round bag picture (`PortraitButton`) is kept out of the grid (`ContainerFrame.xml:321` `smartNavigationIgnoreGrid`) and reached only by jump overrides (`ContainerFrame.lua:3559` `ApplySmartNavOverrideForLeftmostButton`, l.3600).
- The setters are global functions in `Utility.lua`, written for callers that are not secure: they hand the write to `SecureHelper:SetSecureValue` (`SecureHelper.lua:144`), which stores the value from Blizzard's own secure handler. Blizzard's comment (`Utility.lua:14`): "These values may be set without causing taint (only while out of combat)". Device: the same path on one of our own buttons was allowed out of a fight and blocked in a fight (probe trial `pad.mark`).
- A button is told when the cursor arrives and leaves: `OnSmartNavSelect` / `OnSmartNavDeselect` methods, called through a taint barrier (`SmartNavigation.lua:710`, `:680`, `SecureHelper.SecureCallOptionalFunction`, `SecureHelper.lua:210`).

##### Why A does nothing on our tab without help (evidence)

- The bag's footer puts its own action on A: `pickupAction` (`ContainerFrame.lua:3442-3447`), limited to buttons whose `buttonContext` field is `ButtonContext_ContainerFrameItemButton` or `ButtonContext_OpenBagDropdownSettings`, and it stays bound while unusable (default visibility ALWAYS: `PromptedBindings/PromptedBinding.lua:43`; `PromptedBindingFooter.lua:221-241`, `:267-276`).
- `IsConditionMet` (`PromptedBinding.lua:78-106`) fails for a button without that field, and `TriggerBinding` (`:620`) then does nothing. There is one binding per key (`InputBindingStack/InputFunctionBinding.lua:46-50`: `SetOverrideBindingClick(UIParent, true, key, ...)`), so the press does not fall through to the cursor's generic "click".
- We must not give our button a `buttonContext` field: it is not one of SecureHelper's registered keys, so it would be a field written by addon code that Blizzard's footer reads on every refresh, and the footer rebuilds its key bindings in that same call. That is exactly how item use would get blocked.
