# Post-0.0.9 Batch (0.1.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. One task per agent, in order, never two at once.

**Goal:** Build the six items and the debug-log fixes from the eighth device test, one commit each, and ship them as pre-release 0.1.0.

**Architecture:** One addon, one Lua file per feature, no libraries. Each task changes one feature file (plus `Settings.lua` / `Core.lua` where named), its rule tests in `tests/features/`, and the stand-in client `tests/lib/fakeclient.lua` where a new game function is needed.

**Tech Stack:** Lua 5.1 (WoW "Forever", Interface 16001, modern API), LuaJIT offline tests.

**Spec:** `docs/superpowers/specs/2026-11-17-post-0.0.9-batch.md` (the binding authority; each task below names its section).

## Global Constraints

- Read first: `CLAUDE.md`, the spec section for your task, `docs/ARCHITECTURE.md` sections "Adding a feature" and "What the device allows (from the probe)", and the header comment of every file you change.
- With the Gamepad UI on, addon code never opens, focuses or closes the chat box, and never touches the chat edit box. Controller buttons (override bindings) are only taken or given back out of a fight, or from `PLAYER_REGEN_DISABLED`.
- No libraries. Every event handler, timer, hook and frame script goes through `PE:Safe` / `PE:Wrap` or the module's `Wrap` / `Safe` / `RegisterEvent` / `After`.
- Nothing ticks while its feature is off. No new `OnUpdate` and no new per-frame work. Do not change `ACTIVE_INTERVAL` or `SELECT_INTERVAL` in `QuestArrow.lua`.
- New options default to what 0.0.9 does. A saved table from 0.0.9 must load and behave the same.
- Every new game function, global, key name or frame method: find it in `~/.cache/wow-ui-source/forever` (Gethe/wow-ui-source, branch `forever`), quote file and line in your report, then run `scripts/audit-api.sh` (about 45 s; it rewrites `tests/api/*.txt`, commit those). Anything not found there is guarded (type checks, `pcall`) and reported so it can be logged in `docs/ARCHITECTURE.md`. Do not edit `docs/ARCHITECTURE.md`, `PRD.md`, `CHANGELOG.md` or the TOC version yourself; the release task does that.
- Debug log: every new decision path writes one line, as `if PE.debugOn then PE:Debug(key, text) end`. Never per frame. Never a player's name or chat text.
- Tests: add rule tests to the feature's file in `tests/features/` for every rule in your spec section's "Tests" paragraph, written before the code (watch them fail first). Extend `tests/lib/fakeclient.lua` only with what the source shows the game does. Never weaken or delete an existing test to make it pass; if an existing test encodes behaviour the spec changes, change it and say so in the report.
- `scripts/check.sh` and `scripts/test.sh` must both pass before you commit. `check.sh` also rejects owner wording in comments: write comments for a player reading the code (no "the owner", no "device test").
- Commit only your task's files, one commit, message `0.1.0 item N: <what>`. Never `git add -A` or `git add .`: `docs/errorLogs/`, `docs/realtest1/`, `docs/screenshots/` must never be committed, and `PRD.md` / `docs/ARCHITECTURE.md` have uncommitted notes that the release task commits. Never push.
- The player is not an addon developer: every text shown in game is plain language.

### Task 4: The quest arrow follows the player

Spec section 4 (read "What was found" first: do not re-investigate, build the design).

**Files:**
- Modify: `addons/PocketEssentials/QuestData.lua` (`ObjectiveState` returns the matched objective's number; `AddPin` stores it as `pin.obj`; header comment's pin description)
- Modify: `addons/PocketEssentials/QuestArrow.lua` (`Select`, `Nearest`, `ShowDistance`'s leave edge, `StartDriver` / `StopDriver` logging, `OnDisable`, header comment)
- Modify: `addons/PocketEssentials/CONTRACT.md` if it describes pins
- Test: `tests/features/questarrow_test.lua` (and `tests/questiedb/` baseline only if pin counts change, which they must not)

**Notes:**
- Constants: `KEEP_RATIO = 0.8` (a new spot must be under 80 % of the current distance), `KEEP_YARDS = 15`, `ASIDE_SECONDS = 180`.
- Spot identity: map id, `pin.x`, `pin.y`, `pin.obj`. Keep the current target across a rebuild by finding the same position among the new spots; when found, do not reset `S.here` or the distance text.
- Set-aside list: a table keyed by position, value = expiry (`GetTime()`), filled when `S.here` goes from true to false in `ShowDistance`, read and pruned only in `Select`. Cleared on focus change, map change, `OnDisable`. All set aside → clear and pick again.
- "Finished objectives drop at once": `OnData("quests")` already forces a pick on the next update; when the current target is gone, the steadiness margin does not apply.
- Log lines exactly as in the spec's "Arrow debug log". Coordinates as map percent with one decimal ("46.5,73.5"). `DebugState` already writes only when the text changes.
- "driver started / stopped": write them only when the driver goes between "showing an arrow" and "not showing one"; a start that ends in the same text-only state on its first update writes nothing.
- Existing tests that assert the old log text change with it; the tick-budget tests must stay green unchanged.
- Useful real quest for tests: 745 on map 1412 has 26 spots in three camps and three objectives (see `tests/lib/questworld.lua` for how quests and maps are set up; add 1412 there with width 5137, height 3425 if you use it).
